## 已有输入与固定约束

- [需求](requirements-v1.md)：产品以会话为中心，工作区是文件位置而不是安全沙箱；提供真实本地命令行、兼容依赖安装、授权文件访问、省流策略和有条件的自动续跑。
- [ADR 0001](adr/0001-host-pi-durable-in-android-app.md)：主 Agent 的 `pi-durable` 和 `pi-ai` 在本应用运行宿主中运行，不交给外部 Termux 中的 Agent 进程；不以完整桌面 Node/HTTP 后端或 `pi-coding-agent` 为产品基础。
- [术语表](../GLOSSARY.md)：沿用会话、项目、工作区、自动续跑、系统授权和操作审批的现有定义，不重新讨论已确定的产品问题。
- [原型结论](prototypes/README.md)与[已确认原型](prototypes/conversation-ui.prototype.html)：Console 第 2 版是手机、横屏平板的布局与交互基线。
- [ADR 0002](adr/0002-webview-ui-with-kotlin-host.md)：用户已独立确认正式 UI 采用 WebView 页面 + Kotlin 原生宿主。选择依据包括自定义界面扩展，而不只是原型使用 HTML；原型的全局内存状态、示例数据和预览控制条不能作为生产架构。
- [ADR 0003](adr/0003-separate-runtime-host-process.md)：用户已确认运行宿主与 UI 宿主分进程；这不选择 Agent JavaScript 引擎，也不是权限隔离或保活保证。
- 用户已确认 Web 前端采用 TypeScript + React + Vite，宿主与随包界面扩展共用 React；依赖版本尚未固定。
- [ADR 0004](adr/0004-full-termux-environment.md)：采用完整 Termux 环境，以 Android 场景中尽可能广泛的兼容工具与依赖安装能力为优先，不退化为有限工具箱。
- [ADR 0005](adr/0005-managed-external-termux.md)：优先采用本应用与独立官方 Termux 两个 APK；承担首次配置、跨 UID 文件与执行协调，以保留官方包生态。具体发行版本和主应用身份尚未固定；本应用的 API 36 验证基线已另行确认，不改变 Termux 自身 target。
- [ADR 0006](adr/0006-typescript-core-with-native-control.md)：应用业务协调以运行宿主内的 TypeScript 为主，Kotlin 保留 Android 机制和 JS 无响应时的控制；不复制 SDK 状态机，也不把系统授权与操作审批合为一套“权限”。
- [ADR 0007](adr/0007-shared-sdk-storage-for-conversations.md)：产品会话与 SDK conversation 一一关联，全部产品会话共用同一 Storage 和一个活动 Session 写入者，不按会话或项目分拆 SDK 存储域；不由 Q14 隐含决定后端与普通元数据位置；它们后来由 ADR 0008 单独确认。
- [ADR 0008](adr/0008-sdk-documents-and-sqlite.md)：普通应用业务元数据优先复用 SDK document／必要 entry，SDK 主存储以 SQLite 为设计目标；具体驱动、迁移接线与 Android 耐久性仍待验证。
- ADR 排除完整桌面 Node/HTTP 后端，不等于排除应用管理的 Node 运行时。是否采用 Node 仍须选择并验证。

## 目标验证设备与启动体验

用户提供：小米 15、三星 Galaxy S23，并确认两者均为 Android 16；平板计划使用小米平板 9。Android 版本按用户报告记录，尚未直接访问设备；具体厂商 ROM、ABI、页面大小与权限状态仍待核验，不能把出厂系统或公开升级记录当作当前设备状态。

用户已确认启动体验的上限：正常使用中，最多只在首次初始化时要求人工操作。若需要命令，应用必须提供完整命令、执行位置说明和便捷复制，并检查初始化结果。后续启动、连接和恢复由应用负责，不接受重复手工打开终端或输入命令作为正常流程。强行停止、权限撤销等平台阻塞应明确显示，不绕过系统规则。

本文的“受管启动”表示：应用检查执行端是否就绪、在允许时启动或重连、等待就绪确认，并在失联后核验执行状态；它不表示无限保活、无条件后台唤醒或自动重放未知副作用。这是运行管理职责，不是新的产品实体；双 APK 路线已由 Q3-I 单独确认，具体传输协议仍未选择。

## 设计与讨论方法

按 `codebase-design` 的原则设计深 Module：用小 Interface 承接较多行为，把复杂性集中在 Implementation，而不是分散给调用者。

- Interface 包含调用顺序、不变量、失败语义和必要性能约束，不只是方法签名。
- 在真实变化的位置设置 Seam；有明确生产和测试需要时才引入 Adapter，不为了假想可替换性层层包装。
- 用删除测试检验 Module：删除后复杂性如果消失，则可能只是转发；如果扩散到多个调用者，则它有实际价值。
- 调用者和测试经过同一个 Interface，不以测试读取内部状态来掩盖不清楚的职责。
- SDK 已经解决的模型协议、扩展和恢复机制优先复用；宿主补齐 Android 能力与实际执行约束。
- 根选择与 Q27—Q35 已接受。字段、常规 Interface、默认值、持久化接线与测试由代理自主收敛，并区分用户决定、代理细化与待验证事实。仅在改变功能／体验／安全取舍、路线不可行、缺少发布目标或需要新执行授权时集中询问。
- 已澄清的产品术语立即更新术语表。技术细节只记录在技术设计中，不塞入术语表。
- 仅在难以逆转、缺少上下文会令人意外、且实际比较过替代方案时记录 ADR。
- 不再继续逐项技术访谈；最高应用 Interface 的测试 Seam 和纵向切片按既定方向收敛。生产实现、验证工程、安装与设备操作由后续执行授权启动，工单发布本身不是执行授权。

## 设计树与讨论顺序

### 1. 技术栈和运行架构

已确认与当前待决策的上游选择：

- **Q1：正式 UI 路线，已确认。** 用户明确回答“q1 是，正式选择”，采用 WebView 页面 + Kotlin 原生宿主。其前置问题 **Q1-E** 已明确设计方向：支持扩展提供自定义交互界面，以用户已有的 timeline 插件作为参考；具体 Interface 待设计；不承诺旧插件原文兼容。
- **Q2：运行宿主的进程归属，已确认。** 用户回答“q2 是”，采用运行宿主与 UI 宿主分进程，由 Android Service 管理；不由页面生命周期托管 Agent。
- **Q3-E：命令行环境方向，已确认。** 用户明确要求完整 Termux 环境，以 Android 场景中尽可能广泛的兼容安装能力为目标。
- **Q3-I：已确认。** 用户对“本应用 + 独立官方 Termux”两个 APK 回答“可以”。以保留官方包生态为优先，承担首次初始化和跨 UID 协调；普通使用免重复手工启动是硬门槛。不替换、卸载或清空现有 Termux，见 ADR 0005。
- **Q3-T：验证构建基线已确认。** 用户对本应用先以 `compileSdk=36`／`targetSdk=36` 验证回答“可以”，Termux 保持官方发行物自身的配置。不因外部 Termux 而降低本应用 target；没有将验证基线等同于兼容通过或授权开始测试。若替代运行时需要改变条件，须明确复审。
- **Q4：Web 前端框架，已确认。** 用户回答“q4 是”，采用 TypeScript + React + Vite，宿主与随包界面扩展共用 React。
- **Q5：首个验证候选方向已原则认可，Aether 补查已完成。** 用户回答“我觉得是”，同时指定 `Zhou-Shilin/Aether`。现已确认其采用应用私有 Alpine／PRoot 中的 Node 子进程，不是 Javet，也不是外部 Termux 承载主 Agent。复核后维持先小范围验证 Javet Android Node 的建议，不重复要求用户确认同一个顺位；应用自有 Node 子进程成为有真实先例的重要对照，Hermes 仍保留。生产运行时及交付物兼容性尚未确定；ARM64 设计范围已由 Q7 确认，验证工程尚未授权。
- **Q6：SDK 设计与验证基线，已确认。** 用户回答“q6 可以”，采用固定的 Pi Durable / Pi AI `1.5.0` 继续设计和验证。其 SQL、commit、watch、校验及恢复 Interface 不能直接沿用 `1.3.0`。尚未安装或运行新版本，生产可用性仍待验收。
- **Q7：首版兼容投入范围已确认。** 用户同意按 Android 16 起、ARM64 设计，暂不投入旧 Android 和 32 位 APK 适配；先验收小米 15／S23，平板布局与功能保留，计划平板在型号和系统明确后补充设备验证。开发用 x86_64 不扩大产品支持范围，也不限制 Termux 工具安装能力。

之后再确定：

- 本应用内的 Agent JavaScript 引擎及集成方式：本应用身份下的受管 Node 进程、内嵌 Node，或经过适配的独立非 UI JavaScript 运行时。不是借外部 Termux 的 Node 承载主 Agent，也不是让界面 WebView 的 JavaScript 上下文负责后台执行。
- 独立官方 Termux 的具体发行版本、包源与升级联动、许可履约和实际依赖兼容范围；运行时核对其官方身份与前缀，不重新引入自有包仓库。
- SDK `1.5.0` 的实际发布产物与传递依赖锁定、其他工具链版本、ARM64 交付物的实际兼容性、`minSdk` 安装门槛、API 36 基线的验收及安装包组成。

### 2. Module 划分、职责与依赖

在已确认的运行架构与明确的运行时验收条件下，开始讨论行为归属、依赖方向、状态所有者和实际需要的 Seam，不先生成空包装层。具体候选未通过运行验证，不妨碍讨论职责，但不能冒充生产兼容已证实。

- **Q8：业务协调的主语言与职责，已确认。** 用户回答“可以”，由运行宿主内的 TypeScript 核心承接会话与工作区协调、应用策略、SDK 接入和领域记录的组织；Kotlin 承接 Android 生命周期、系统授权等平台事实及必要控制。Pi Durable 保留自己的执行／恢复状态机。JS 无响应时的原生紧急控制必须保留，具体持久记录仍待设计，见 ADR 0006。
- **系统授权与操作审批已再次明确。** 前者由 Android 管理，首版仍按实际规则申请和检查；后者是应用逐操作请求批准，首版 YOLO 不实现。省流、停止、初始化就绪、身份和执行结果检查不是操作审批，不建设审批队列或空审批框架。
- **Q9：工具环境 Module，已确认。** 用户回答“都可以”，集中工具文件访问、命令生命周期、就绪、输出、取消及结果核验，通过 SDK 环境 Adapter 使用；核心据其执行事实决定工作恢复，不让 UI／各工具分别控制 Termux。
- **Q10：核心与扩展的关系，已确认。** 持久化与停止／恢复不变量、平台检查和实际执行控制入口留在固定核心，扩展通过 Interface 使用；不把所有机制插件化，不改变已定的真实 UI、UI-only 与内置能力共用扩展机制。
- **Q11：模型配置 Module，已确认。** 统一模型配置与凭据访问，复用 Pi AI 和平台凭据能力；不另造 Provider 框架，不选择具体存储、加密或审批行为。
- **Q12：扩展登记关联，已确认。** 用户回答“可以”，以一份薄的应用描述关联可选 UI 与 Agent 贡献入口，各宿主只加载自己的入口，Agent 贡献仍使用 SDK registry；显式检查身份误重复，不禁止 SDK 已支持的有意工具／section 覆盖。不新增插件框架或热重载承诺。
- 详细取舍与剩余依赖见 [Module 设计](module-design.md)。工作区协调已归 TypeScript 核心，不重问所有权；锁范围、持久记录和中断条件留后续设计。

### 3. 核心领域模型与数据持久化

Module 职责与扩展登记已确认，当前进入本层。保持已有产品领域语言，不把内部执行机制变成独立产品任务。详细取舍见 [领域模型与持久化设计](data-design.md)。

用户已逐项确认以下根选择：

- **Q13：产品／SDK 会话映射，已确认。** 每个产品会话关联一个 SDK conversation，延续多轮历史与恢复；内部 SDK 会话不自动出现在产品列表。
- **Q14：SDK 逻辑存储组织，已确认。** 所有会话共用同一 Storage，同一时刻由一个活动 SDK Session 拥有写入；不选择物理文件数量、引擎，也不强制所有会话串行执行。
- **Q15：工作区身份，已确认。** 稳定内部记录加引用，而不是到处复制 cwd 字符串；不能因不同记录指向同一目录，就绕开写入协调。
- **Q16：附件内容与来源，已确认。** 留存实际作为模型输入的稳定内容版本，并另记原始资源引用；不完整归档每个原件，也不以副本修改冒充原文件修改。
- **Q17：模型选择作用域，已确认。** 共享 Provider 配置与凭据，新会话采用创建时默认模型、之后各会话独立保留选择；首版不另加项目级模型继承。
- **Q18：文字草稿耐久性，已确认新增范围。** 每会话文字草稿跨应用重启保留，不自动发送；附件草稿随后由 Q24 单独确认。

输入草稿、待确认提交、SDK 已接纳输入和 transcript 不混同；SDK 控制 document 也不是普通 UI 缓存。这些是事实与正确性约束，不重复投票。

用户已对以下 8 项回答“都可以”，均已确认，详见[数据设计](data-design.md)：

- **Q19：普通应用元数据，已确认。** 复用 SDK 自定义 document／必要 entry，不另建竞争的主业务数据权威；具体文档作用域与时间语义随后明确。
- **Q20：SDK 存储后端方向，已确认。** 以 SQLite 为初始设计目标；具体驱动、Android 兼容与耐久契约尚未验收，不授权安装或建库。
- **Q21：已开始工作的位置，已确认。** 保留其实际项目／工作区绑定版本，不随后来配置修改途中换位置；不冻结文件内容或系统授权。
- **Q22：会话切模型的生效政策，已确认。** 沿 SDK 逐尝试规则：后续 prepare 可用新选择，普通重试也可能采用新模型；在途、正常 close 后的原请求恢复、deferred 轮询和已选 compaction 按各自原规则处理。
- **Q23：文字草稿持久化归属，已确认。** 原生侧独立保存，不等待 Agent JS 启动或正常响应；不转移 SDK 历史与执行权威。
- **Q24：附件草稿，已确认新增范围。** 保留来源引用与必要的已生成内容，重启核验可用性，不完整复制每个原件；这是新增范围。
- **Q25：未确认的发送意图，已确认。** 与草稿分开持久保存，保持目标、内容关联和提交身份，恢复后核验或重试同一次提交；不许借投递恢复绕开停止。
- **Q26：保留原则，已确认。** 正式历史与仍需引用的输入内容不自动过期；可重建缓存可清，空间不足和保存失败可见，不表示无限容量。

[应用记录设计](data-records.md)中的 **Q27—Q35，均已确认**：当前值元数据、连接身份、原生输入记录归属、附件准备与固定、接纳及使用中的位置约束、凭据密文保护、锁屏后台可用性、系统备份排除、延后单会话物理删除。具体后端、字段、预算、引用释放、迁移、通信与完整恢复流程由代理在[首版 spec](specs/v1/spec.md)收敛；实际驱动与兼容性由验证工单证实。

### 4. Interface 与通信协议

依赖 Module 职责和数据所有权。

收敛契约见[首版 spec](specs/v1/spec.md)：命令与查询、状态快照／订阅、耐久与接纳确认、重复提交、流式更新、大输出引用、版本和重连。逻辑 Interface 固定；本应用绑定 Service 为首选接线，外部执行传输通过受管启动验证后固化，不把传输候选当作已测事实。

### 5. 关键流程、状态管理与异常恢复

依赖前述 Interface 和持久化规则。

## 技术选择与代价（逐项标明状态）

### Q1：WebView 页面 + Kotlin 原生宿主（已确认）

最初建议 Compose，理由是原生系统接入较直接。用户追问 WebView 有何问题后，重新评估：需要原生宿主不等于必须使用原生 UI，该理由不足以优先排除 WebView。

就已确认的界面而言，主要工作是聊天长列表、Markdown、代码／文件 diff、弹层和手机／平板响应式布局。Web 技术与这些内容型界面匹配，有现成的渲染与布局生态；当前没有已知需求构成 WebView 的硬性障碍。因此调整建议，优先考虑 WebView；用户随后于 2026-11-03 正式确认该选择，而不是因原型恰好使用 HTML 就直接沿用它。

职责方向（具体 Interface 尚未冻结）：

- Web UI 负责呈现、输入和局部交互状态。Q4 已选定 TypeScript + React + Vite，具体依赖版本待验证后固定。
- Kotlin 宿主负责 WebView 集成及必要的 Android 能力接入，包括系统授权、文件选择、系统返回和运行宿主连接。
- Agent 的执行、恢复和权威持久化状态不由页面 JavaScript 生命周期持有。采用 WebView 不自动决定 Q2 的应用进程划分。
- 页面可以随 APK 打包，通过本地资源加载和原生通信接入运行宿主；不需要因此引入 Node/HTTP 服务器。

需要承担的工程成本：

1. 键盘弹出、输入法组合输入、底部安全区、返回行为、文件选择与授权需要 Android 集成和真机检查。
2. 长聊天、大 diff 和流式输出需要分页／虚拟化与合并更新等适当策略；不能因 WebView 就断言性能不够，也不能免除验证。
3. 页面／渲染进程退出后，需要重新连接并读取运行状态。不能把恢复检查点仅放在页面内存或依赖 WebView 的存储访问路径中。
4. 原生通信入口必须受控：加载可信的打包页面，限制来源和导航，校验输入；模型回复、Markdown、工具输出等不可信内容不能变成可执行脚本。不向页面暴露任意原生调用或直接执行任意命令的入口。
5. 同样需要 Kotlin 与 TypeScript 协作。原型的布局经验可以保留，但其单文件全局状态、模拟数据和事件处理不能直接作为生产实现。

Seam 应放在 UI 与应用行为之间，以少量高层命令和状态订阅连接深 Module，而不是逐个镜像底层 Android 或 SDK 方法。这样可以在不改动执行／恢复规则的情况下维护 Web UI，并从同一个 Interface 测试应用行为。

Compose 不再作为并列待选方案。若实际验证发现 WebView 无法满足关键要求，必须明确复审本决策，不能静默削减界面扩展能力。正式选择记录见 [ADR 0002](adr/0002-webview-ui-with-kotlin-host.md)。

实现参考：[本地页面资源加载](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content)、[原生通信安全](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)、[WebView 管理](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview)。具体集成尚未验证。

#### Q1-E：界面扩展的表达能力（方向已确认，具体契约待设计）

用户担心原生 Android UI 会导致前端页面的扩展点无法充分开放。不能把这直接解释为原生 UI 不可扩展，也不能把选择 WebView 当成已自动具备扩展机制。

区分两类能力：

- **声明式贡献**：扩展提供导航项、按钮、配置字段或数据，由宿主已有的渲染规则呈现。Compose 和 WebView 都能承载。
- **自定义交互界面**：扩展提供自己的页面、面板或结果展示逻辑。Compose 可通过随包编译的 Kotlin 界面实现，也可采用受限描述格式或嵌入 WebView；但不能直接使用 Web 界面代码。WebView 对使用同一 Web 框架编写的 TypeScript 界面接入更自然。

用户回答“最好是可以的”，并举出以前使用 Pi Durable 时实现的自有 timeline 插件。因此按支持自定义交互界面的方向设计，不将扩展能力限定为固定表单；记录为明确设计目标，不擅自增加具体插件的移植交付。首版仍是开发者编写、随应用打包的可信代码，不新增动态插件安装或插件市场要求，也不承诺跨 UI 框架或桌面插件直接兼容。

timeline 作为真实设计样本，可用于检查界面挂载、数据读取／订阅、当前会话上下文以及局部交互状态等需求。不要求现在重写插件，也不将旧实现兼容性视为已验证。

只读搜索找到一个较强候选：`C:\Users\AI_BA\.pi-pocket\extensions\user-messages.ts`，配套 `user-messages/index.js`、`model.js`、`style.css`。它的启动关键词包含 `timeline`，但尚未确认就是用户提及的插件，不据此推断作者。

候选源码体现的真实需求：

- 使用 Pi Pocket 提供的 Preact hooks 和 `htm`，通过宿主注册 panel、menu 与 launcher；这些是应用 UI 扩展能力，不是 Pi Durable 内核自带的注册字段。
- 订阅当前会话变化，通过带游标的消息读取 Interface 获取历史；可见页面每 5 秒轮询。轮询间隔只是参考实现，不是新应用的要求。
- 提供搜索、刷新、历史分页、取消加载和定位消息等交互。稳定消息标识、取消与销毁清理属于 Interface 的实际需求。
- 扩展把消息快照保存在内存中；历史记录和面板布局持久化由宿主负责。源码未见该扩展直接依赖 Android 原生能力。

可借鉴这些职责与能力契约，不直接移植它的多人筛选、面板布局系统或整套宿主后端。具体需保留的交互、数据形态和消息协议在后续设计中确定。

已确定允许仅贡献界面的扩展，不为接入可视化强制注册虚假的 Agent 工具。一个应用能力可以按需提供两部分，Q12 只决定它们如何登记关联：

- 内核部分继续使用 Pi Durable 的工具、提示词、hooks、执行协作及状态机制。
- 界面部分通过应用自己定义的 UI Interface 注册贡献，并关联对应能力；它不是 Pi Durable 自带的页面注册机制。

候选接入位置包括导航及对应页面、设置／会话详情中的区域、工具结果的专用展示、平板辅助面板。具体位置集合、生命周期与消息协议在 Module 和 Interface 讨论中再确定，不为所有 DOM 节点设计 hook。

按照深 Module 原则，界面宿主集中处理导航、挂载、作用域上下文、响应式容器、状态连接和错误降级。扩展在稳定的 Seam 提供内容与动作，不依赖宿主内部 DOM，也不直接取得数据库、运行进程或通用原生调用入口。前后端代码可关联同一能力，但不会因此共享同一 JavaScript 运行上下文。

扩展执行的可信前端代码与模型／工具输出中的不可信 HTML 必须区分。首版可信随包扩展不构成第三方代码沙箱；不能将模块约定或错误兜底宣传成强隔离。

建议选已有内置能力（例如一种工具结果展示）走同一注册路径，验证扩展无需修改核心聊天页面即可贡献界面。不是先建一批空注册函数，也不为验证扩展机制新增未确认的产品功能。

### Q2：独立的应用内运行宿主进程（已确认）

2026-11-03，用户明确回答“q2 是”。选择记录见 [ADR 0003](adr/0003-separate-runtime-host-process.md)。

理由：将执行生命周期与页面生命周期分开，减少 UI 重建或 UI 侧故障对运行内核的直接影响。UI 发命令、订阅状态，不自行驱动 SDK 恢复或打开同一份 SDK 存储。

代价：增加进程通信、重连和内存开销。具体 JavaScript 引擎是否内嵌或作为受管子进程，留到后续选择。

限制：分进程不等于持续存活。应用被强行停止、设备重启或系统回收仍按已有恢复要求处理。有执行时按系统规则使用前台运行，不承诺常驻。

已比较的替代：同进程 Android Service 加独立执行线程可以减少通信复杂性，但 UI 与内核共享进程故障范围；用户已选择分进程，不再将两者列为同等待选。分进程本身不授予独立 UID、额外系统权限或对子进程的硬性断网能力。

### Q3：完整 Termux 环境（方向、独立 APK 与 API 36 验证基线已确认）

用户先要求解释目标 SDK 与 `termux-exec`，随后明确表示需要完整 Termux 环境，目标是 Android 场景中尽可能广泛的工具和依赖安装能力。因此环境方向已确认，记录见 [ADR 0004](adr/0004-full-termux-environment.md)；这不等于接受此前的内嵌方式、应用身份或 target 28 组合。

#### Q3-E：完整环境与安装能力优先（已确认）

- 保留完整包管理及按需安装、升级兼容工具和依赖的能力，而不是只打包几个命令。
- 完整环境不要求预装全部仓库，也不把 Termux 终端界面、全部附加 APK 或任意 Linux 软件兼容性自动纳入交付承诺。
- 若某种集成方式妨碍广泛包兼容，应重新比较集成方式，而不是静默削减工具安装能力。
- 执行环境仍须由应用管理，不能要求用户每次手工启动终端或后端；首次配置的可接受程度在 Q3-I 明确。

#### Q3-I：保留包生态的集成方式（独立官方 Termux 已确认）

[打包与前缀研究](research/termux-packaging-options.md)核验：官方命令包针对 `com.termux` 及 `/data/data/com.termux/files/usr` 构建，包含构建期路径。改变应用 ID 后，单纯改 `$PREFIX` 或使用 `termux-exec` 不会使整个官方仓库自动可移植。

此前比较了 3 条路线；用户现已确认第 1 条为优先部署路线，第 2、3 条保留为取舍记录，不是并列未决选项：

1. **独立 Agent APK + 官方 Termux APK**：保留官方身份、路径和包源，尽量减少仓库维护；代价是独立应用依赖及一次初始化、授权。两个 UID 的控制、文件交换和生命周期需要设计。
2. **保留 `com.termux` 身份的融合 APK**：在同一身份下保留环境并接入新界面；不能与现有 Termux 作为两个独立应用并存，签名不同也不能直接作为普通更新覆盖。命令包的仓库签名与 Android 附加 APK 的签名要求不同，须分别处理。不默认用户接受替换或数据迁移。
3. **自有应用 ID + 内嵌完整环境**：避免占用官方身份，但原生执行路线需要重建匹配前缀的 bootstrap、所提供的包及依赖，并持续维护仓库。不能承诺只重建 bootstrap 就拥有整个官方仓库的安装能力。

路径映射／PRoot 可另行研究，但尚未证明在改名 APK 中能无修改兼容整个仓库，不把它列为已验证的免费替代。

[受管外部启动研究](research/termux-managed-startup.md)确认：`RUN_COMMAND` 支持不打开终端 Activity 的命令启动。首次仍需 Termux 安装、bootstrap 初始化、外部调用授权与配置；不能承诺首次全静默。完成回调不等于流式通信，也没有现成的按执行 ID 取消操作；必须在 Termux UID 内补充可管理的执行协议，不能把取消回调当作停止进程。

用户进一步澄清：主 Agent 仍在本应用自己的运行宿主中，Termux 只是命令执行端。`pi-durable`、`pi-ai`、主会话调度与恢复决策属于应用；Termux 可以执行 Bash、Python、Node、包管理器和其他工具，但不承载主 Agent。应用内具体 JavaScript 引擎和持久化布局仍待选型验证，不能把“Termux 可以安装 Node”当作应用内 SDK 已能运行的证据。

在已选外部环境中，实际命令进程属于 Termux；应用不因此直接拥有其私有目录或进程句柄。Termux 内可以有受管的执行桥，用于命令启动、流式输出、取消、状态核验及相关执行记录，但它不是另一个主 Agent，不接管整个会话的调度。工作区与文件访问必须跨 UID 明确设计；主会话状态的权威所有者仍是本应用。

职责澄清当时没有单独选择 APK 形态；之后用户已明确接受双 APK 路线，记录 [ADR 0005](adr/0005-managed-external-termux.md)。不再询问是否接受独立 Termux，也不授权将 Pi Durable 迁到外部环境以规避适配。

正常使用仅首次初始化允许人工处理，必须提供完整可复制命令并检查就绪；普通冷启动和恢复不能靠反复手工打开 Termux。如果该硬门槛无法实现，须复审方案，而不是自动接受单 APK 重建或削减要求。

#### Q3-T：目标 SDK 与执行机制（API 36 验证基线已确认）

用户已确认本应用先以 `compileSdk=36`／`targetSdk=36` 验证，外部 Termux 保持选定官方发行物自身的配置。两侧 target 分别适用，部分跨 APK 规则还要同时检查双方条件，不能只看一个数值。

此前曾比较利用低 target 的可写目录执行兼容性，但用户没有选它作为本应用的默认路线。Javet Android Node 默认通过 APK 原生库加载，与把独立 Node 放入可写目录再 `execve()` 不同；不能为了完整 Termux，就把 Agent APK 一并降到 28。

此处确认的是验证基线，不是 JNI、SDK、后台运行或原文件访问已经通过。若后续 Node 子进程候选需要不同打包或兼容条件，必须明确复审，不静默改变已确认的方向。具体事实见 [Android 16 宿主研究](research/android16-host-baseline.md)。

首版 Android 16 起、ARM64 范围已通过 Q7 确认。`targetSdk` 不是最低安装门槛，也不是设备系统版本；`minSdk` 与实际依赖、交付物和支持范围一同落实。有限解释器工具箱仍不是完整 Termux 的替代。

#### Q3 的机制解释

- `minSdk` 指应用可安装的最低 Android API 级别；`compileSdk` 指编译所使用的 Android API 集合；`targetSdk` 用于声明应用面向的目标行为与兼容规则。三者不是同一个开关。
- API 28 对应 Android 9，但 `targetSdk=28` 不表示只能在 Android 9 上运行，也不要求使用旧版 React。较新的编译 SDK 与设备 WebView 仍可使用；具体系统能力和目标版本相关行为需分别核验。
- 动态安装命令行程序通常意味着把 Android 兼容的二进制及依赖写入应用可写目录，然后启动它。Android 10 对目标为 API 29 及以上的应用从可写应用目录直接 `execve()` 有限制，正好影响这种安装与运行方式。
- Android 16 AOSP 仍有低 target 的私有目录执行兼容规则；这只说明存在一条可研究的兼容路线，不代表已经在用户设备上验证安装、权限和工具运行。低 target 也不取消其他 Android 系统限制。
- 下载脚本交给已可运行的解释器读取，与直接启动新下载的本机二进制不同。现代 target 并不等于不能运行命令行；系统链接器执行适配、APK 打包运行时／解释器等都是候选，但须验证新工具及兼容依赖的安装能力。

以下保留 Termux 执行兼容机制的取舍背景，不表示重新选择本应用 target、改变官方身份或建设自有包仓库：

1. **Termux 兼容环境 + 较低 target**：预计减少直接启动私有目录二进制的适配障碍；接受部分旧兼容行为，以及未来系统或厂商收紧安装／执行策略的风险。
2. **Termux 兼容环境 + 较新 target**：研究 `termux-exec` 等执行适配，减少对低 target 兼容规则的依赖；需验证启动拦截覆盖、子进程、解释器链和实际工具兼容性，不能承诺已可用。
3. **此前的受限环境候选已排除**：只打包少量运行时／解释器、仅保证有限脚本依赖安装的方案，不满足用户已确认的完整 Termux 方向。可借鉴其打包技术，但不得借此替换或削弱包环境。

两条 Termux 兼容路线都还需要处理应用包名前缀、库依赖、ABI／页大小、包源和更新维护。私有目录执行兼容不使官方 Termux 包自动可移植，也不支持任意桌面 Linux 二进制。

后续验证应包含实际应用身份下的 Bash／解释器启动、代表性工具及依赖的安装与升级、用户已授权原始文件的读写，以及子进程中断与恢复闭环；没有据此执行安装、修改设备或启动生产实现。完整 Termux、独立官方 APK 路线和本应用 API 36 验证基线均已确认，实际兼容结果仍待验收。

`termux-exec` 的具体机制与限制见[专项研究](research/termux-exec.md)。当前文档的 `system_linker_exec` 默认模式为按条件启用，不等于所有程序都使用 linker 路径；直接系统调用、静态 ELF、环境继承和可观察进程身份均需验证。研究还发现环境清理行为的文档／源码差异，正式验证必须固定实际包与源码版本，不能把可变 `master` 文档当作已部署行为。该机制研究没有执行真机测试，研究事实本身不是选型批准；后续用户确认的本应用 API 36 验证基线以 Q3-T 为准。

### Q4：TypeScript + React + Vite（已确认）

2026-11-03，用户明确回答“q4 是”。以 TypeScript 编写界面与界面扩展，React 提供呈现与交互组织，Vite 负责开发与构建；构建产物随 APK 打包，不在 APK 中运行 Vite 开发服务器，也不为 UI 引入 SSR 后端。

理由：当前需要可组合的自定义界面扩展、富文本、复杂结果展示和长列表，React 的相关生态有利于实现这些能力。代价是框架与依赖体积、渲染更新管理及扩展对选定框架的耦合；不能将生态优势当作真机性能保证。

已比较的替代是 Preact 或 Vue。找到的 timeline 候选使用 Preact，但其身份尚未确认，宿主 Interface 也不同，因此这不构成必须采用 Preact 或能直接复用旧插件的证明。库版本与具体渲染库另行核验。

宿主与随包界面扩展共用 React，不为了假想的全框架兼容提前建立多套渲染抽象。具体 Interface 和扩展打包方式仍在后续讨论中决定。

## 已核验的事实与未验证项

核验日期：2026-11-03。只做文档和源码检查，本轮没有 Android 真机测试。

1. 本机安装的 `@earendil-works/pi-durable`、`@earendil-works/pi-ai` 均为 `1.3.0`，两者的 `engines.node` 都为 `>=22.19.0`。这不是已选择的生产版本，也不证明非 Node 引擎不可行。
2. Durable 有可移植的 `/storage/sqlite`、`/storage/jsonl` 和 `/env` 接入点；Node Adapter 则使用 `node:sqlite`、`node:fs` 和 `node:child_process` 等能力。
3. SDK 1.3.0 的 SQLite Interface 要求 `exec`、`run`、`get`、`all`、`transaction`、`close`；1.5.0 另要求 `runCounted`，并将数据库类型移至 Chord 后转导出。两版均要求事务外操作排队，事务内使用事务句柄；不能把普通 SQL 转发等同于满足契约。
4. Durable 的存储契约与 schema 由 SDK 定义；同一 storage 要有单一进程所有者，不能假设 SDK 提供跨进程协调。
5. Pi AI 的浏览器／Provider 入口与 Node 依赖必须按实际导入图核验。流式响应需要增量读取、UTF-8 解码和取消；替换 `fetch` 不自动适配 WebSocket。
6. Android 10 对 `targetSdk>=29` 从可写应用目录直接 `execve()` 有限制。AOSP 的低 target 兼容规则不能直接证明某个应用和全部包在每台设备上可运行。
7. SAF 提供文档 URI，不是通用 shell 路径。文件访问方案必须操作已授权的原始文件，而不能用仅操作上传副本来冒充满足需求。
8. 前台运行不消除系统回收与子进程限制。ABI、16 KB 页大小、包前缀、进程树取消、后台恢复和网络变化都需要实际验证。
9. Pi Durable 1.3.0 的 `Extension` 声明包含 `name`、`tools`、`sections`、`hooks`、`wraps`、`tasks`，没有页面或 UI 注册字段；本轮按固定 1.5.0 源码再次确认此形状。`ToolExecutionResult` 的 `details` 是面向 UI 的数据，不是渲染器。页面扩展 Interface 由应用宿主定义，不要求重建 Agent 内核。历史来源为本机声明；当前来源与注册、覆盖及生命周期细节见 [1.5.0 扩展组合审计](research/pi-sdk-1.5-extension-composition.md)。

补充研究还确认了以下集成约束；细节与版本范围见各专项报告：

- SDK 1.3.0 的 SQLite schema 使用 `STRICT` 和 `json_valid`。Android API 33 的标准 SQLite 不满足其 `STRICT` 门槛；运行时自带或另行打包 SQLite 均需能力与事务验证。
- `Shell.exec()` 不自带持久执行标识与重连收据。unsafe Bash 恢复返回 `interrupted`，不会自动查询 Termux 实际结果；不能把 Bash 改成 safe 来掩盖不确定副作用。
- `Harness.close()` 与用户主动取消不同。恢复安全策略必须覆盖实际执行，不能仅放在不重跑的 `beforeTool` hook 中。
- 共享模拟外部存储的 `noexec` 和链接限制会影响工具构建。文件工具与 Bash 必须看到一致的命名空间，不能直接把外部 Termux 的路径交给本应用 `node:fs`。
- Javet Android Node、Moose、VHEditor 和 AcodeX 分别提供运行时、Pi 集成、自有包生态和执行桥的源码证据，但没有一个已查项目替代了本项目的完整验收。
