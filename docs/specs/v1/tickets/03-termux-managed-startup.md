# T03：验证首次配置后的官方 Termux 受管启动

实施验收：T03 限定开发前置条件已通过，依据已有 S23 矩阵及用户授权的实际 Android 16 模拟器锁屏／重启补验；[证据与限制](../../../../termux-probe/validation.md)。S23 对应生命周期与 T17 双真机验收仍待补齐，不把 4 KB 通过当作固定 x86_64 Termux 的 16 KB bootstrap 问题已修复。

## What to build

交付最小初始化与执行探针闭环：用户只在首次初始化完成安装、配置及系统授权，此后从本应用触发探针，应用自行启动或重连官方 Termux 执行端并显示真实结果。验证双 APK 路线是否达到正常启动免重复人工处理的硬门槛。

## Acceptance criteria

- [x] 固定官方 Termux 发行物、来源／签名、版本、包源和实际 target；本应用保持独立身份及 API 36 验证基线，不占用 com.termux 或降低本应用 target。
- [x] 初始化界面分别检查安装、bootstrap、RUN_COMMAND 系统授权、allow-external-apps 配置和执行桥版本，不把某个保存的“配置完成”标记当就绪。
- [x] 必要手工步骤提供完整命令、执行位置、便捷复制及执行后核验；不要求用户搜索／拼装命令，也不默认替换、卸载或清空现有 Termux。
- [x] 真实探针验证 shell、必需工具、可用工作位置以及执行端身份／版本握手；Intent 发出成功、进程存在或最终回调到达均不能单独表示全部能力就绪。
- [x] 首次配置完成后，分别验证普通应用冷启动、仅执行桥死亡、Termux 进程死亡、应用进程回收和重启首次解锁后的合法启动／重连；正常场景无需再打开终端或粘贴命令。
- [x] 缺失／撤回系统授权、外部调用配置失效、执行端不兼容、force-stop、系统禁止启动与无法识别的超时分别呈现；无法证明原因时保留未知，不误报为用户未初始化。
- [x] 重复点击、并发连接和超时重试不会启动多个执行端实例；超时有界，可重新核验，不靠无限等待掩盖启动失败。
- [x] 演示兼容工具与代表性依赖的安装、运行和升级，记录具体包和结果；完整环境保留按需安装能力，不退化为预置命令集合，也不声称任意 Linux 包兼容。
- [x] 合法前台运行、通知权限／渠道状态、锁屏与厂商后台限制有实测记录；不以 specialUse、低 target 或 wake lock 宣称无限后台运行。
- [x] 形成目标场景矩阵和可复现证据。若普通启动／恢复仍反复依赖手工打开 Termux，本门槛失败并触发部署路线复审，不把手工排障改写成正常流程。

## Blocked by

无（与 T01 可并行；执行仍须另行授权）。

## Implementation notes

- 已确认：Termux 只拥有工具执行；主 Agent、SDK 和恢复决策始终归本应用。两个 APK 的 UID、授权与私有存储不互通。
- 自主细化：通过官方 RUN_COMMAND 引导最小执行桥，后续连接具备调用者认证、版本和实例身份核验；探针只执行固定测试命令，建立可沿用到 T09 的真实边界，不先搭建通用 RPC 平台。
- Kotlin 持有初始化、启动、连接与平台原因事实；Termux 报告自身实际能力。失败保存可核验诊断，不能自动改用户全局设置或用绕过授权的命令修复。
- 具体握手／传输可以在验证中选择最小合适方案；成功证据必须包含实际跨 UID 路径，不用桌面模拟器的同 UID 测试替代。

## Test seam

从应用的“初始化／检查执行环境”高层入口验证一个真实命令完成，使用实际 Android 调用路径和官方 Termux。对无响应、旧实例、重复回调和权限变化用受控故障注入补充。参考 Aether 的复制命令与探针、Termux 官方入口，但不把参考源码当本项目测试通过。

## Scope and execution boundary

本票不交付完整命令流、可靠执行收据或会话恢复，分别由 T09／T12 承接。安装 APK、变更系统授权／Termux 配置、包安装升级、编写验证工程及真机操作均需后续明确执行授权；ready-for-agent 仅表示设计就绪。现有 Termux 数据不得因验证被替换、卸载、清空或迁移。
