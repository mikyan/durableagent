# 执行环境与 Console 后续改进

2026-11-05，用户更新当前工作目标。本记录补充首版 spec；用户的新要求优先于旧 UI 组织方式。Termux 来源兼容继续按 [兼容契约](termux-compatibility.md)，不能以连接成功代替工具执行成功。

## 用户要求

1. 修复真实 bash 调用返回“执行连接未确认结果，保留原身份等待核验”的问题。保留原身份与未决记录；找出原始失败边界，不通过重装、清空、重新配对或自动重发掩盖失败。S23 为代理实际验证设备；Xiaomi 15 上公开 v0.1.0 的相同现象是用户报告。
2. Agent 的系统上下文必须明确 Android 平台、独立 Termux 执行环境、当前实际工作区以及已知能力/连接状态。应用内 Agent 与 Termux 的进程、UID、文件可达范围不同；不得把应用私有目录写成工具当前目录，或把未知状态说成已连接。
3. 页面切换与相关展开交互加入平滑过渡，保留键盘、焦点和导航状态，遵循减少动态效果偏好。
4. 移除会话页独立横向“发送状态”框；思考中、工具执行、排队、发送待确认、停止及错误在消息流中呈现。界面变化不合并发送意图、SDK 接纳、模型执行和外部效果这几种不同事实。
5. 补全当前固定 pi-ai SDK 支持的所有 Provider 入口，并使用其实际协议与认证实现。旧连接继续可用；不得只添加选项却仍把所有请求送往 chat/completions。
6. 模型页面一级展示 Provider 与当前模型，点击特定 Provider 才进入 token/登录/模型配置的二级页面，参考 Hermes Console 的实际交互。移除该页“本机数据”“运行宿主”内容；Termux 独立为连接页面并明确使用“Termux”名称。

## 代理细化

- Provider 目录来自已安装 SDK，而非手写一份容易漂移的清单。API Key 与 OAuth 凭据继续由原生加密存储承载；公开配置只返回状态，不返回秘密。
- OAuth 只由用户明确登录动作开始；界面可以显示授权地址、步骤、输入提示和进度，不能把 token 写入一般模型配置、会话、日志或浏览器本地存储。
- 系统环境信息来自固定平台事实与当前绑定的公开状态；组装提示词不隐式联网核验来源、重新连接或初始化 Termux。
- 动画与消息状态以真实应用状态为依据；没有实际生成/工具事件时不展示虚假的“思考中”。
- 会话公开快照可附 `activity: {kind: 'thinking' | 'tool' | 'model', label?: string}`。仅运行中基于 SDK 当前 generation 与 running tool slot 投影；工具只提供名称，不附参数或输出。思考状态只在实际 thinking 内容块成为当前生成阶段时出现，不输出思考正文或签名。仅接纳输入、待启动工具、恢复等待及结束状态不伪造 activity。
- 已配对执行环境的只读就绪探测 `ping` 返回 `CONNECTION_ABSENT` 或 `CONNECTION_UNCONFIRMED` 时，允许在原有总计 10 秒期限内通过固定 `RUN_COMMAND serve-existing` 唤醒一次，再按原证书、执行端 ID 和账本代次认证。后台冻结的 Termux 可能仍保留监听端口，超时不等同于监听不存在，也不证明原用户操作未发生。这条恢复规则只用于业务请求发送前的就绪探测；不重配对、初始化、清空账本或重发 `prepare`、`start`、文件修改等用户操作。身份、协议和权限等其他错误仍拒绝；共用启动锁、取消资格检查、来源离线核验和期限保持原约束，期限耗尽明确失败。
- 就绪探测与实际请求使用不同 socket，OEM 可在两者之间再次冻结 Termux。实际请求的连接、TLS 或只读 `hello` 阶段仅在本地传输明确证明业务帧尚未尝试写出时，才可产生原生内部的“未派发”标记；不能从公开 `CONNECTION_UNCONFIRMED` 错误码推断。认证拒绝、协议/身份错误、原生停止/省流检查失败不产生此标记。从业务帧长度前缀开始尝试写出起，部分写入、等待响应和断连均保持结果未知，不自动重发。
- 非显式连接的每次原生请求从入队起共享 30 秒预算，包含最初就绪探测、所有子请求、一次额外恢复唤醒及其后认证/派发；TypeScript 的 40 秒等待保留余量。最初就绪探测最多一次唤醒，额外恢复最多再唤醒一次（合计最多两次固定启动），由“明确尚未派发后重新认证”与“保留原 socket 的在途唤醒”原子共享。发送前恢复保留同一配对与业务请求，离开原生存储作用域后才唤醒，随后重新读取必要的只读 `list`/`query` 证据；在认证后、业务帧写前重新检查关闭/取消资格、停止代次和省流事实。任何已经尝试派发的原业务请求不能进入重新发送分支。
- 业务帧开始尝试写出时，可安排一次 1 秒延迟的在途唤醒提示；原 socket、requestId、会话 nonce 和当前帧读取位置持续保留，不重发帧、不从部分读取处重新开始解码，也不延长请求期限。独立定时器只提交有界 worker，worker 再核验离线来源、强行停止状态、权限、原配对、关闭资格和剩余期限，只派发固定 `serve-existing`，不另发探测或初始化。在同一应用进程内，以启动锁及等待开始时的启动代次合并同配对的重叠唤醒；不宣称跨进程统一协调。
- 正常回执、原 socket 超时和关闭均撤销尚未承诺的定时/排队唤醒。最终派发许可通过原子状态与完成事件线性化：完成先发生时不派发；固定系统调用已承诺时，完成不等待该 Binder 调用或 worker。额外额度仅在实际派发前争取，已完成、失效或被同配对已有启动合并的提示不消耗额度。唤醒失败不覆盖原 socket 的结果，更不把未知效果说成未执行。该机制不使用全局唤醒锁或无限保活。

## 验证范围

用户明确要求 Provider 部分开发后不用测试，本轮不新增 Provider 测试或逐项联网验证；类型检查与打包用于确保代码可交付，不冒称 Provider 在线兼容已实测。既有仓库 CI 保持运行，页面结构改变时同步维护其中的旧导航及文案断言，不扩展 Provider 或 UI 测试矩阵。

核心执行故障保留已取得的失败证据，使用最小诊断定位，并分别记录源码检查、构建、S23 实际工具执行及真实 LLM 的结果。用户已澄清第 0 项要求：测试不能只让模型说“你好”，至少必须实际调用工具。最终用真实 LLM 取得环境信息、调用 bash，并核对真实输出；不据单个 ping 或 bootstrap 通过宣称 bash/文件/恢复通过。所有未取得的设备或 Provider 证据保持未测。

后台冻结回归使用真实 `:agent` 进程中的 `ExecutionChannelDiagnosticTest#namespacedJavetPingInAgentProcessPreservesNativeCode`：记录 Termux 前台成功、退到后台并被系统冻结后的相同调用结果及原始错误码，再在修复版本重跑该链路与完整 SDK 的 bash／文件场景。该设备边界同时覆盖冻结监听器、原生启动和原配对认证；纯错误码分支测试不能代替它。最小探测成功仍不等于完整工具或真实 LLM 验收通过。

`ExecutionOperationBudgetTest` 仅覆盖原生恢复策略的明确未派发、未知响应不重放、二次失败、取消、共享期限及拒绝语义，不模拟或宣称 OEM/TLS 边界已实测。双 socket 冻结窗口仍通过同一 S23 完整 SDK 文件链和真实模型命令验收，记录安全的原生方法/传输阶段及最终错误码，不记录命令参数、密钥或原始 TLS 错误消息。

`PendingExecutionWakeTest` 补充定时与排队阶段完成/失效撤销、等待期间启动代次、派发准备后的资格重查、worker/唤醒失败隔离，以及已承诺系统调用阻塞时原 socket 完成不等待。恢复预算另覆盖在途/发送前恢复共享额度与并发争取。以上调度与策略测试不替代真实 `file.writeResult` 已发送帧后的冻结验收。
