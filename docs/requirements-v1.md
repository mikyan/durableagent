# Android 本地 Agent：首版需求对齐稿

状态：需求对齐稿；界面原型及 Q27—Q35 数据政策均已于 2026-11-03 获用户确认。普通技术细节由代理自主收敛为 spec／工单，尚未开始产品实现或真机验收。

本文记录用户在需求对齐中明确的能力、体验与范围；旧 Hermes 会话中由助手补充的功能表不自动构成需求。产品术语见 [GLOSSARY.md](../GLOSSARY.md)，已形成的架构决策见 [ADR 目录](adr/)。

## 1. 产品定位

- 面向个人自用的 Android 本地 Agent，适配手机和平板。
- 工作在 Android 本机执行，能够使用该设备已授权的资源；不以远程控制 PC 作为主要产品形态。
- 模型可以在云端运行，本地 Agent 不等于离线模型。
- 是通用个人 Agent，不限定为相册整理器或移动 IDE。
- 首版不以 Google Play 上架、商业账户体系或广泛机型覆盖为前提。
- 用户提供的目标手机是小米 15、三星 Galaxy S23，并确认两者均运行 Android 16；平板计划使用小米平板 9。型号与系统版本按用户报告记录，不代表已访问设备或通过兼容验收；具体 ROM、ABI、页面大小和权限状态仍待实际核验。
- 用户已确认首版按 Android 16 起、ARM64 设计，暂不投入旧 Android 和 32 位 APK 适配。先用现有两部手机验收；平板布局与功能仍属首版，计划平板的准确型号与系统确定后补充设备验证。开发用 x86_64 模拟器不扩大产品支持承诺，也不因此限制 Termux 的兼容工具安装能力。

## 2. 产品以会话为中心

### 2.1 会话与项目

- 会话是产品的基本工作单位，交互记录和执行状态围绕会话组织。
- 不引入独立的产品级任务实体、任务卡、任务中心或另一套任务管理流程。
- 新建会话不要求先创建项目、选择目录或建立新的工作目录。
- 用户可以手工创建和选择项目；项目关联工作区，但项目与会话不是同一个概念。
- 未关联项目的会话使用默认工作区。
- 不同会话的历史和执行状态独立；使用同一目录时共享其中的文件。工作区不是安全沙箱。
- 标题、项目名称和普通设置提供当前值，首版不新增完整编辑历史；投递、恢复和执行核验仍需的版本继续保留。

### 2.2 交互形态

用户已确认 Console 参考原型第 2 版，作为后续手机和平板界面实现的布局与交互基线。确认记录及原始原型见 [原型说明](prototypes/README.md)。

- 手机界面以 Hermes Console 为明确设计基线，不再从多个无关的视觉方向发散；参考其页面组织、视觉层级和交互，而不是移植其完整后端或全部功能。
- 保留独立首页；聊天页面保持简单，但完整展示上下文占用、当前模型和操作审批模式。原型中的“权限模式”标签对应此含义，不表示 Android 系统授权状态；首版仍为 YOLO，不因此增加审批界面。
- 聊天输入区保留添加图片与文件的入口；聊天页面右上角的加号可以直接新建会话，不强制先选择项目。
- 不采用输入框上方的上拉横线入口。在附件加号左侧增加独立的详情／配置按钮，统一手机和平板的打开方式；面板限制可视高度，内容内部滚动。
- 附件入口打开贴近输入框的紧凑菜单，而不是大尺寸底部弹窗。
- 长对话中，当对应的用户输入离开可见区域时，以会话内浮条显示该输入，便于对照回复。它不是独立 PiP 助手或系统级悬浮窗。
- 手机上的其他功能通过侧栏组织；各详细页面采用一致的顶栏几何布局、标题和操作区，首页可有独立布局。
- 平板优先考虑横屏，充分利用空间：侧栏默认展开，对话右侧可展开文件变更等辅助信息。平板仍沿用 Hermes Console 的视觉体系；Pi Pocket 桌面端仅作为大框架的信息布局参考。
- 会话的执行、等待、失败和完成状态应当可见。
- 用户已确认首版由原生侧独立保存每个会话尚未发送的文字草稿，不等待 Agent JS 正常运行；重开应用后恢复已保存内容，绝不自动发送，具体保存频率另定。
- 用户已确认由原生侧独立持久保存附件草稿记录、必要内容的持有关系和未确认 SDK 接纳的发送意图，不依赖 Agent JS 正常响应；附件重开时恢复引用及必要的已生成内容，不完整复制每个原件。来源失效时明确提示，不拿缩略图冒充原输入。
- 编辑期间逐步进行本地附件读取／转换，不默认把未发送内容交给云端模型或启动会话工作。交给 SDK 前固定并持久保存实际输入表示；准备不完整时不能宣称内容已接纳，来源变化或超出输入／准备预算要明确失败或提示可选缩减，不静默换内容或丢弃正文。
- 已发起的发送意图保留目标会话、固定内容关联与稳定身份；中断后核验或重试同一次提交，不把重连当成再次发送，也不把未发送草稿自动提交。迟到确认或清空不能覆盖用户后来的新编辑。
- 保存失败和接纳未确认要如实呈现，不能用 UI 已显示冒充已耐久或已接纳。
- 不因参考截图而引入 Cron、独立任务中心、宠物或多 Agent 管理。右侧文件变更区域也不自动扩展为完整文件树、终端或独立产物预览与导出系统。
- 当前验证这些页面的原型不代表附件、文件变更、上下文统计或 Android 后台能力已经实现。

### 2.3 跨会话路由

- 不设独立 PiP 助手或第二个聊天入口。
- 普通会话可以按需查询其他会话的状态、创建会话或向指定会话转交请求。
- 默认在当前会话处理输入，不把每条消息自动分流或包装成新对象。
- 跨会话操作应明确目标；不默认混合所有会话的上下文。

## 3. 本机执行与文件能力

- 在 Android 本机提供较完整的 Bash／命令行能力，支持常见脚本、管道、重定向与命令行工具，而不是有限的模拟指令。
- 能够读取、写入和修改用户授权的手机文件，不局限于应用私有目录。
- 允许按需安装兼容的工具和依赖，不把每次增加工具都变成重新发布应用的要求；以 Android 场景中尽可能广泛的兼容安装能力为目标，不收缩为有限的预置命令工具箱。
- 能获取命令输出、执行状态和结果，并配合停止、中断识别与恢复处理。
- 执行环境由应用管理。正常使用中，最多只在首次初始化时要求用户人工处理；初始化后不得反复要求用户打开终端、启动后端或重新输入启动命令。
- 首次初始化若需要命令，应用必须准备可直接复制的完整命令，说明执行位置，提供便捷复制，并检查初始化是否成功；不把查找、拼接命令或诊断就绪状态交给用户。
- 强行停止、权限撤销等系统阻塞必须明确显示，并遵守系统限制；这不是允许把一般冷启动失败降级成日常手工操作。
- 同一工作区中，可能修改文件的会话执行保守串行；无法判断副作用的命令按可能修改处理。聊天、状态查询和确定无副作用的读取不因此全部停下。
- 通过 SDK 接纳事务核验并固定项目／工作区位置绑定，排队输入、追加输入、自动后继工作及内部会话沿用相应绑定；尚未确认接纳的发送保留已知位置预期，配置已变时明确报告不一致，不悄悄改投新目录。这不冻结文件内容或系统授权，也不把工作区变成沙箱。
- 仍有未结算输入、可执行的相关后台任务及后代、其他会话对共享位置的活动使用、未决受管效果或仍可能投递的发送意图时，拒绝相应会话项目关联及共享项目／工作区位置修改；不能只看 idle。修改不自动排队，条件解除后需重新发起；必要时可另开会话使用另一可用位置。

这里规定能力和体验。后续技术讨论已选择完整 Termux 环境，并确认优先采用本应用加独立官方 Termux 的两个 APK 路线，见第 10 节；具体发行渠道、版本和升级联动仍待决定；本应用已选 API 36 作为验证构建基线，但不能将这些设计决定混同为已经通过验收的产品能力。

## 4. 自动续跑是首版硬门槛

### 4.1 恢复体验

- 会话的必要执行进度应持久保存。
- 已持久化正式历史及仍需引用的必要输入内容默认不按时间自动淘汰；可重建缓存可以回收，空间不足和保存失败必须可见。这不承诺无限容量、完整原件备份或永久保存全部运行日志。
- 遇到可恢复中断后，条件重新具备且系统允许运行时自动继续，不需要用户再发送“继续”。
- 已确认完成的工作不应无故重复；中断不应令整个会话从头执行。
- 当前在做什么、为何等待、何时重试以及是否失败，应当可见。

### 4.2 Android 情境

| 情境 | 首版要求与界限 |
|---|---|
| 网络中断后恢复 | 执行条件满足且系统允许运行时自动继续 |
| 进程被系统回收或异常终止 | 保存进度，在进程获准重新启动或用户打开应用后自动继续 |
| 手机重启 | 首次解锁且系统允许运行后尝试自动继续，不承诺固定唤醒时间 |
| 首次解锁后再次锁屏 | 凭据不额外要求每次／近期认证或保持当前解锁，可继续具备后台调用条件；仍遵守系统运行限制 |
| 在系统设置中强行停止应用 | 不绕过系统限制，等待用户重新打开应用 |
| 用户主动停止会话中的执行 | 不被自动恢复逻辑重新启动 |

恢复不等于进程永不退出，也不等于应用能越过 Android 的系统限制。可以引导用户配置后台运行、自启动或电池优化设置；相关能力受限时必须明确说明。

### 4.3 不确定结果与重试

- 对中断后结果不明的操作，先核验实际结果，再决定是否继续或重做。
- 无法核验的副作用不盲目重放；停止相关操作并说明情况。这是恢复正确性要求，不是要求首版增加操作审批界面。
- 未完成的模型请求允许有界、可见的自动重试。
- 不承诺模型请求绝不重复计费，也不无限重试。

### 4.4 本地保留、备份与删除范围

- 首版的会话／执行数据、业务元数据、草稿、发送意图、必要输入内容、原生控制记录及凭据等私有工作数据排除系统自动云备份和设备间迁移。
- 当前安装内“不自动过期”不等于备份；卸载、清除数据、丢机或换机后不承诺自动恢复。应用升级保留本地数据与卸载重装不同。
- 排除规则需要覆盖实际存储布局、云备份、设备迁移及新增通道，并在目标设备核验；一个备份开关不构成所有厂商迁移都被阻止的保证。本应用不统一控制外部 Termux、用户原件或任意提取工具。
- 单会话持久历史的物理删除不作为首版交付门槛，不把隐藏、撤回输入、清空模型上下文或退休 document 冒充彻底删除；不因此新增归档或隐藏功能，也不影响 Agent 按用户请求操作可用原文件。
- 可证明无引用的应用临时材料仍可按清理规则回收；不据此删除必要历史、有效输入内容或未知效果的唯一核验证据。迁移／版本错误须可见并保留原数据，不静默清空重建。

## 5. 省流模式

- 省流模式限制受限网络上的非模型网络活动，同时保留模型通信与受控的纯本地操作。
- 我们控制的联网操作应服从统一网络策略；非模型通信等待条件恢复，或由用户明确临时放行。
- 已界定为纯本地的受控操作可以继续，不将所有 Bash 操作一律暂停。
- 未纳管或联网行为不明的命令在受限网络下等待，或由用户明确临时放行。
- 程序路径可以用于识别，但不能仅因某个程序被打包进应用，就认定它及其任意脚本、参数和子进程都不会联网。
- 运行中的网络变化也应得到处理，不能只在命令启动前判断一次。
- 这是一套受控工具的省流策略，不承诺任意代码的系统级硬断网或网络切换瞬间零流量。

具体网络判定和执行机制属于后续设计，不在需求中锁定为某种防火墙、VPN 或进程隔离方案。

## 6. 系统授权、操作审批与模型数据

### 6.1 首版默认 YOLO

- 首版按 YOLO 执行可用工具，包括兼容依赖安装；不实现应用内逐操作审批流程、审批队列或审批弹层。
- 后续操作审批模式应有明确接入位置，不应要求重写 Agent 核心；首版不因此建设完整审批子系统或空审批框架。
- Android 系统授权仍按实际机制申请、检查和处理拒绝或撤销；操作审批模式不能替代或扩大系统授权。界面中的 YOLO 不代表全部系统权限已经授予。
- 区分依据是 Android 的资源／能力授权与应用额外的逐操作批准，不是弹窗次数。系统可能针对新资源或特定系统操作要求再次交互；正常启动不重复手工配置 Termux，不等于以后不再出现必要的系统授权。
- 省流、用户停止、工作区串行、环境就绪和结果核验仍然生效；等待这些条件不是等待操作审批。网络临时放行仍按既有省流要求处理，不另建通用审批队列。
- Termux 的外部调用配置属于执行环境初始化，不等于 Android 系统授权，也不是逐命令操作审批。
- 不新增逐文件或云端上传等单独的应用内审批流程。

### 6.2 云端模型

- 聊天内容、附件及工具结果可能进入所选模型的上下文；在模型配置中清楚说明这一点。
- 不增加逐文件的云端传输审批，不将只读误称为数据不出本机。
- 用户已确认保留实际作为模型输入的稳定附件内容版本，并与原文件引用区分；原件变化不改写当时采用的内容。此要求不等于完整归档每个原文件，也不保证原文件授权永久有效；修改副本不能冒充修改原件。
- 首版不要求实现自动识别所有敏感信息的防泄漏系统。

## 7. 模型接入

- 首版支持 API Key 配置；订阅账号 OAuth 登录不作为首版门槛。
- 复用 `pi-ai` 的 Provider、模型目录、端点配置、协议、流式响应及鉴权能力，不另写一套通用 LLM 接入框架。
- 应用提供必要的配置入口、安全凭据存储与 Android 运行环境适配。
- 用户已确认共享 Provider 配置与凭据，设置新会话默认模型；新会话初始化自己的模型选择，此后各会话独立保留，修改默认值不自动切换老会话。首版不增加项目级模型继承，不将 Key 复制到各会话。
- 用户已确认会话模型切换沿 SDK 的逐尝试规则：后续新 prepare 可采用新选择，普通生成重试也可能采用新模型；不因设置修改强行中断或重发在途请求，已有 deferred 响应及已选压缩请求按原规则处理。
- 模型服务目的地或不兼容协议变化使用新的连接身份，保留仍被旧选择／检查点引用的必要旧定义；不自动切换既有会话或把旧 Key 交给新服务。连接约束覆盖鉴权可能覆盖的端点，旧请求无法兼容恢复时明确说明，不静默改用新连接重发；停用、账户变化和凭据轮转仍须核验。
- Keystore 保存保护密钥，API Key 密文保存于应用私有 CE 存储；不将 Keystore 描述为可直接取回 API Key 的字符串仓库。暂时不可用、永久失效、密文损坏和格式不兼容应区分；保护密钥丢失／失效后要求重新配置，不降级为明文，也不删除会话历史或新草稿。
- 为支持锁屏后台续跑，保护密钥不额外要求每次／近期认证或当前保持解锁；手机重启后仍须首次解锁及系统允许运行，不增加 Direct Boot 模型执行。代价是获授权的应用锁屏后仍可使用密钥，不提供逐次用户在场保护。
- 合法请求仍在请求进程内使用必要的明文凭据；普通查询与广播不返回原始 Key，凭据不得混入 SDK 持久化请求选项。Keystore 不替代错误、日志及通信的防泄漏处理，也不构成同 UID 进程或可信随包扩展之间的秘密隔离。
- 对具体 Provider 和端点的可用性，以所选 Android 运行环境的验证结果为准，不把 SDK 中存在某个 Provider 等同于已经完成真机支持。

## 8. 首版就具备真实扩展点

- 扩展性是首版架构要求，不是后续补几个空接口。
- 开发者可以编写与应用一同打包注册的扩展；内置能力也使用同一扩展接入机制。
- 用户已确认同一功能用一份薄的应用扩展描述关联可选的界面入口与 Agent 能力入口；各宿主只加载各自代码，Agent 贡献仍交给 SDK 注册。意外重复的扩展身份在装配时报错，不禁止 SDK 已支持的有意工具覆盖；具体格式与字段仍待设计。
- 界面扩展以支持自定义展示与交互为设计目标，不只允许填写宿主预设的按钮和表单。用户已有的 timeline 插件是此类能力的参考；其具体移植或直接兼容不自动成为首版交付门槛。
- 允许 UI-only 扩展通过宿主已有能力查询、订阅和交互，不为它强制注册空的 Agent 扩展或虚假的工具；这不表示 UI-only 完全不使用核心查询。
- 复用 Pi Durable 的扩展能力，支持增加工具、提示词片段、执行协作和扩展状态，而不是再造一套 Agent 核心。
- 后续长期记忆、更多工具和操作审批等应用策略应能通过明确的扩展或宿主接入点增加；Android 系统授权仍由系统管理，不由扩展策略自行授予。
- Agent 可以通过宿主提供的能力管理自身设置；首版不要求热更新应用核心代码。
- 首版不要求从手机动态安装 JavaScript 插件，不要求插件市场。
- 不承诺所有 Pi Coding Agent 桌面扩展未经适配就能使用。

## 9. 不自动扩大首版范围

以下能力不作为首版交付门槛：

- 从其他应用通过 Android 分享菜单导入；这与聊天输入区内选择图片和文件的入口不同。
- 专门的产物预览与导出体验；这不排除第 2.2 节中用于对照会话的文件变更区域。
- 独立的网页搜索或抓取功能。
- 长期记忆；后续按插件能力规划。
- 全量元数据编辑审计、单会话历史物理删除、系统自动换机恢复、凭据导出及云同步；具体保留和恢复边界见第 4.4 节。
- 定时执行、专门的子代理编排、无障碍或 ADB 手机操控、桌面协同与 IM 桥等尚未要求独立交付的增强功能。

“不作为门槛”不等于禁止通过已有通用工具完成相关工作。未明确提出的能力也不因旧草案列过就自动进入首版。

## 10. 已明确的技术约束与未选方案

### 已明确的约束

- 主 Agent 在本应用自己的运行宿主中运行：使用 `pi-durable` 作为内核，复用 `pi-ai` 进行主 Agent 模型接入，会话调度与恢复由本应用负责；不把主 Agent 放进外部 Termux 进程后由应用界面遥控。
- 用户已确认以固定的 Pi Durable / Pi AI `1.5.0` 作为后续设计与验证基线。生产可用性仍需验收，不因此安装 SDK、自动升级本机工具或直接套用 `1.3.0` 的 Adapter。
- 用户已确认本应用先以 `compileSdk=36`、`targetSdk=36` 进行验证，不因外部 Termux 的 target 而降低本应用 target；Termux 保持所选官方发行物自身的配置。这不是已完成运行时或后台验收，也不是开始验证工程的授权。
- 不以移植完整桌面 Node/HTTP 后端作为产品基础。理由见 [ADR 0001](adr/0001-host-pi-durable-in-android-app.md)。
- 正式页面采用 WebView，Android 原生宿主采用 Kotlin，以支持自定义交互界面扩展并适配手机和平板；这不决定 Agent 的运行时或进程划分。理由见 [ADR 0002](adr/0002-webview-ui-with-kotlin-host.md)。
- 运行宿主与 UI 宿主分进程，由 Android Service 管理运行；分进程不等于持续存活或权限隔离。理由见 [ADR 0003](adr/0003-separate-runtime-host-process.md)。
- Web 前端采用 TypeScript + React + Vite；宿主界面与随应用打包的界面扩展共用 React，构建产物随 APK 打包，不在 APK 中运行 Vite 开发服务器。
- 用户已确认应用业务协调以运行宿主内的 TypeScript 核心为主，Kotlin 承接 Android 机制与 JS 无响应时的必要控制；不在 Kotlin 复制 SDK 状态机，也不把系统授权与未来操作审批混为一套“权限”流程。见 [ADR 0006](adr/0006-typescript-core-with-native-control.md)。
- 采用完整 Termux 环境作为命令行基础，负责 Bash、脚本、包管理和其他工具进程，优先保留尽可能广泛的兼容工具与依赖安装能力；它不承载主 Agent，完整环境也不等于预装所有包或移植 Termux 终端界面。理由见 [ADR 0004](adr/0004-full-termux-environment.md)。
- 优先采用“本应用 + 独立官方 Termux”两个 APK 的部署路线，保留官方包生态；不由本应用占用 `com.termux` 身份或维护自有前缀仓库。首次初始化之后免重复手工启动仍须验收，不自动允许替换、卸载或清空现有 Termux。见 [ADR 0005](adr/0005-managed-external-termux.md)。
- 用户已确认工具文件访问与命令生命周期统一由工具环境 Module 承接，核心根据执行事实决定恢复；固定核心保留持久化、停止／恢复及平台检查等不变量，业务工具和界面功能通过扩展接入；模型配置与凭据访问共用应用拥有的 Module，调用协议仍复用 Pi AI。具体存储、通信和加密实现未随这些职责选择一并确定。
- 用户已确认每个产品会话关联一个 SDK conversation，全部产品会话共用同一个 SDK Storage，同一时刻由一个活动 SDK Session 拥有写入；这不混合会话上下文，也不要求会话执行全部串行。见 [ADR 0007](adr/0007-shared-sdk-storage-for-conversations.md)。
- 工作区具有稳定的内部记录，项目／会话按既定关系引用；记录身份、实际目录和访问能力分开，不因不同记录指向同一目录就绕开写入协调。
- 普通业务元数据优先复用 SDK 自定义 document／必要 entry，SDK 主存储以 SQLite 为设计目标；原生控制、凭据和草稿等按职责组织，不承诺跨来源原子提交。具体驱动和 Android 兼容仍待验证，见 [ADR 0008](adr/0008-sdk-documents-and-sqlite.md)。
- Pi Durable 内部的任务属于实现机制，不因此在产品中引入独立任务对象；产品仍以会话为中心。

### 尚未选定或验证

- 独立官方 Termux 的发行渠道／版本、现有安装兼容、签名核验、包源及升级协调；本应用自身的包名与签名。部署已选外部官方环境，不再把自有前缀仓库列作同等未决方案。
- Agent JavaScript 运行时、前端与运行时的依赖版本、运行时／命令行环境的具体打包方式，以及 `minSdk` 安装门槛；API 36 验证基线已定，生产设置仍须通过兼容验收。
- Android 存储、文件、执行和模型传输适配的具体实现。
- 实际设备和系统版本上的运行、后台恢复及兼容范围。

这些问题通过技术方案比较和验证解决，不伪装成已经确认的产品需求。

## 11. 首条验收闭环

在手机上打开一个不关联项目的会话，让 Agent 处理一批真实存在、已获授权的手机文件；中途制造网络中断或终止进程，在条件恢复后继续处理。

验收关注：

1. 不需要先创建项目或新的工作目录。
2. 能操作真实手机文件，而不只是应用内上传副本。
3. 已保存的进度可恢复，不要求用户重新发起同一请求。
4. 已完成的操作不无故重复；结果不明的操作先核验，不盲重放。
5. 文件结果符合要求，聊天中能看到结果、状态或异常原因，完成后可以通知用户。
6. 用户主动停止后不会自动复活。
7. 首次初始化之后，普通启动与恢复不要求再次手工开启执行环境；首次必需的命令由应用提供并支持直接复制。

不要求为这一闭环先做分享入口、专门的产物查看器或独立任务页面。
