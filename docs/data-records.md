# 应用记录：语义、权威与生命周期

状态：Q13—Q35 均已由用户确认；Q27—Q35 的确认按 2026-11-03 交接补记。区分已定语义、由语义推导的约束和仍需自主细化／验证的实现。本文不是数据库 DDL、最终字段清单、通信协议或实现授权；生产驱动与 Android 行为仍须验证。决定与取舍见[数据设计](data-design.md)。

## 1. 概念记录图

```text
共享应用事实
  项目 ──引用──> 工作区 ──当前绑定──> 执行环境限定的位置
  新会话默认模型 ──引用──> 模型配置
  模型配置 ──关联──> 独立管理的凭据

产品会话 ──一一关联──> SDK conversation
  ├─ 可选项目关联；未关联则使用默认工作区
  ├─ 自己的模型选择；不复制凭据
  ├─ 草稿：尚未发送
  └─ 发送意图：已明确发起，可能尚未确认接纳
          └─ 接纳后关联 SDK submission / inbox / entries

已开始工作使用的位置绑定 ──保留实际采用的关联与位置版本
附件输入版本 ──稳定内容表示 + 可用的原件引用
工具执行事实 ──独立核验；不能用 SDK 状态代替
```

箭头是语义关联，不表示必须使用 SQL 外键、同一物理数据库或同一个事务。这里的记录不是新的产品任务、任务中心或独立助手。

## 2. 由已定方向推导的记录职责

下表是逻辑模型，不将示意名称固定为代码标识或文档 kind。

| 记录／事实 | 必须表达什么 | 权威与不得推导的含义 |
|---|---|---|
| 产品会话登记 | 哪个 SDK conversation 是用户可见的产品会话，以及其产品身份 | 应用普通业务记录，按 Q19 接入 SDK；不把所有内部 SDK conversation 自动登记进首页，不要求两种 ID 相等 |
| 会话展示与关联 | 标题、项目关联等应用事实；可重建摘要与不可重建用户设置要区分 | SDK 中的应用记录或有来源的投影；不另造全部消息正文权威 |
| 项目 | 具名上下文及工作区引用 | 共享应用事实，不向每个会话复制一套独立项目权威 |
| 工作区 | 稳定身份、当前定位依据与执行环境关联 | 记录 ID 不等于目录，不代表访问能力；不同 ID 指向同一目录不能绕开协调 |
| 已采用的位置绑定 | 工作实际使用的项目／工作区关联与位置版本 | Q21 已要求恢复后可核验；不冻结文件内容，不把旧授权状态当当前授权，也不复制 SDK 执行状态机 |
| 模型配置与默认选择 | 可用连接／模型的非秘密定义、新会话默认选择 | 共享应用事实，由模型配置 Module 解释；Q28 已确认目的地或不兼容协议变化使用新身份，必要旧定义继续保留；停用与凭据兼容细节仍须落实 |
| 会话模型选择 | 该会话当前选用的模型 | 通过 SDK 的会话配置维护，并沿 Q22 生效；不另建不同步的第二份运行模型权威 |
| 文字草稿 | 尚未发送的文字及区分新旧编辑所需的版本关系 | Q23 已确认原生侧持久保存；React 内存中仍可能有未保存编辑，不能宣称每次按键已耐久 |
| 附件草稿 | 已选资源引用、必要的已生成表示和可用性依据 | Q24、Q29 已确认保留范围及原生持久化归属；不能把原件引用等同于永久访问权 |
| 发送意图 | 明确的发送动作、目标会话、固定输入关联与稳定提交身份 | Q25、Q29 已确认由原生侧独立持久保存；不代表已被 SDK 接纳，不是新的 Agent 任务队列 |
| 附件输入版本 | 本次真正采用的稳定输入表示及可用原件引用 | Q16 已确认；可以是图片表示、文本或片段，不承诺完整原件归档或最终 Provider 报文快照 |
| 原生停止意图 | 用户已要求停止及抵御迟到恢复所需的控制事实 | 原生控制职责；不能等待无响应的 JS，也不能直接修改 SDK 私有表来制造执行终态 |
| 外部执行证据 | 工具环境的接纳、运行、停止和结果核验事实 | 工具环境所有，核心解释；PID、SDK 终态或单个完成通知都不单独证明全部外部效果 |

### 不需要重新投票的约束

- 产品会话、SDK conversation、发送意图、SDK submission、entry 与外部执行各有自己的身份含义；不用相同正文推断是同一次发送。
- 同一次发送重试不能换目标、换内容或生成另一份主动发送身份；主动再发一次即使文字相同，也可以是新的发送。
- 保存或确认某个草稿版本，不能让迟到回调覆盖、清空后来的新编辑。
- 新会话默认模型用于创建时初始化；既有会话的选择不跟随全局默认改变。
- 原生草稿／发送意图与 SDK 接纳不自动处于同一事务；具体协议需要核验与恢复，不靠先后两次成功调用冒充原子提交。
- 系统授权、当前网络、原件存在与执行端可用性必须依据当前事实。持久记录可以说明过去发生了什么，不能代替现在的许可与结果。
- 数据版本、存储提交收据和工具执行收据不同。采用 SQLite 不会让 Android 授权或 Termux 副作用加入该数据库事务。

## 3. SDK 接入约束

依据[数据政策核查](research/pi-sdk-1.5-data-policy.md)：

- `session` document 可以承载共享应用事实，但其生命周期不是一次 Android 进程运行。具体 family／singleton、kind、索引与字段属于后续 Implementation 设计。
- conversation document 的 `latest`、`rewindable` 与 fork 政策必须匹配语义；不能用字段版本迁移偷偷改变已有实例的这些规则。
- 产品登记和会话模型初始化可以与 SDK conversation 创建共同提交。首次发送仍是另一个操作，需要稳定关联，不能把创建成功当成发送已接纳。
- SDK 的 `pi.agent`、inbox、live、Provider 身份与用量沿各自真实契约维护；应用元数据政策不能覆盖它们。
- 原生输入记录不会因为 SDK fork 自动变成另一份用户草稿或主动发送。内部会话如何获得执行上下文与是否登记为产品会话，是不同的问题。
- Models／settings getter 是同步 Interface。settings 可能在 `Harness.open()` 期间读取；有效启动值与完整配置就绪必须分别落实，调度入口不能绕开就绪检查。
- SDK 图片输入仍要求内联 base64；文件、URI 或 blob ID 只作为应用元数据保存时，不会自动变成模型可读图片。不得以“内容外置”为由悄悄改变 SDK 字段契约。

## 4. 本轮新增事实，不作为真假投票

[SDK 输入与退休核查](research/pi-sdk-1.5-input-and-retirement.md)及 [Android 私有数据研究](research/android-private-data-and-backup.md)均已完成，未运行 SDK 或设备测试。

- SDK `requestId` 只在同一 conversation 内按同类型去重，不比较输入内容；同一身份的内容一致性由应用保证。
- 多条 submission 可加入同一 run，一个 run 可交接多个 generation task。`pi.live.run.taskId` 会变，不是稳定的工作组 ID；自动后继 run 也不保证中间出现 idle。
- `Conversation.submit(tx, draft)` 支持接纳与应用文档共同提交，但 admission 必须先于 table write。conversation 创建已是 table write，不能由此声称创建与首次提交可在该 overload 中合并。
- 没有通用事务型 run-start／inbox-consumed hook。`beforeRequest` 已晚于环境准备；安全工具重放可跳过 `beforeTool`；generation prepare 还会捕获 env builder 异常并继续，因此仅在 env 中抛错不是完整的执行闸门。
- task-owned conversation 自动复制父 `pi.agent`，不自动复制应用工作区绑定。创建事务可以显式传承上下文，产品登记仍应独立。
- `waitForIdle()` 不等于所有输入、后台任务、后代或外部效果都已结束；不能单凭它放开位置修改或回收记录。
- SDK 1.5.0 没有公开删除／退休 conversation、entry、submission 的 Interface。`retireDoc()` 结束文档实例，SQLite 可以删除 current-only revision，但这不删除会话历史，也不证明安全擦除；fork 仍可能依赖祖先 entries。
- Pi AI 已有自定义 Provider ID 与新旧定义共存能力；同 ID 的替换仍会改变旧引用的解析。保留定义不自动保留凭据，也不能忽略鉴权结果中的端点覆盖。
- Android Keystore 保存密码学密钥，不是任意 API Key 字符串的可读写仓库。可以用其保护密钥加密 API Key，密文放私有 CE 存储；请求进程仍会获得必要明文。
- CE 存储在重启后首次解锁前不可用。Keystore 的每次／近期用户认证和“当前设备必须解锁”是独立附加条件；不设置这些条件也不绕过系统运行限制。
- `allowBackup=false` 不能单独保证所有 D2D 迁移被禁止。云、设备迁移及后续新增通道需分别配置和验证；本应用规则不控制外部 Termux 或用户原件。
- 原生 SQLite 和 Multi-process DataStore 都有可用事务语义，适用的数据规模不同；SharedPreferences 不提供可靠跨进程协调，`apply()` 返回也不代表耐久保存。原生后端选择须跟随记录归属决定。

## 5. 已确认：Q27—Q35

用户于 2026-11-03 回复“都可以按你说的来”，接受本节全部 9 项政策及其安全、可用性、备份和删除取舍。后续普通字段、Interface、持久化接线与测试安排由代理基于既定方向收敛，不再逐项访谈；改变已接受承诺、发现路线不可行、缺少发布目标或需要新的执行授权时，再集中确认。

### Q27：普通元数据提供当前值，不新增全量编辑审计

**已确认：标题、项目名称和普通应用设置按当前值组织，不为首版提供每次编辑的完整历史；仍需用于投递、恢复或执行核验的版本另行保留。**

- 这是应用自有元数据的语义，不覆盖 SDK `pi.agent`、transcript、inbox、live 或用量的历史与控制契约。
- 已采用的位置绑定、仍被请求引用的连接定义和必要输入版本，不因“只提供当前值”而丢失；跨来源引用尚未核清时也不能视为无用。
- `latest` 不等于磁盘上从未有旧值，也不是安全擦除保证。实际 checkpoint／revision 回收仍按 SDK 契约处理。
- 不新增历史改名查询、全量设置审计或分支聊天界面；具体 document scope／kind 是落实语义的 Implementation，不让用户逐字段投票。

**取舍：**减少无必要的历史、迁移与查询复杂性；代价是不能重建每次临时改名或未用于执行的中间设置。

### Q28：目的地或不兼容协议变化使用新的模型连接身份

**已确认：改变模型服务目的地或不兼容协议定义时，建立新的连接身份，不覆盖仍被旧选择／检查点引用的定义；凭据轮转另行处理。**

- 使用 Pi AI 已有自定义 Provider ID 与 collection，不另建 Provider 协议框架。显示名称改变不必产生新的执行身份。
- 目的地约束须覆盖配置中的端点及鉴权结果可能覆盖的端点，不只检查 UI 显示的 URL。
- 新连接不会自动切换既有会话，也不会自动把旧 Key 交给新的服务。新选择与凭据关联必须明确，但不增加逐请求操作审批。
- 保留的是必要旧定义，不是承诺保留失效秘密或永久允许旧连接执行。停用、凭据撤销、账户变化和 deferred handle 的兼容性仍要核验；不能从任意 API Key 自动推断账号相同。
- 旧请求不可恢复时如实说明，不静默改用新连接重发。保存定义也不等于保存旧 SDK 实现或保证远端持续可用。

**取舍：**避免旧请求恢复时悄悄改投另一服务；代价是需要明确替代连接与旧定义的保留／停用关系，而不是编辑一个字符串就覆盖所有引用。

### Q29：附件草稿与待接纳发送意图也由原生侧持久化

**已确认：延续原生文字草稿，将附件草稿记录、必要内容的持有关系和未确认 SDK 接纳的发送意图也交给原生侧保存，不依赖 Agent JS 正常运行。**

- 原生侧负责未发送／待投递输入的耐久保存与版本关系；TypeScript 核心仍负责业务校验和工作协调，SDK 负责已接纳输入与执行，不迁移主 Agent 或复制 SDK 调度器。
- “有发送意图记录”不等于输入表示已经准备好、SDK 已接纳或外部效果已完成。未完成准备的记录不可直接投递。
- 原生可以保存引用并持有必要文件，不意味着把附件字节塞进同一张表，也不选择物理数据库数量。
- 原生归属已定，原生 SQLite／DataStore、共同提交范围和草稿清空时点由后续设计落实；不因 Q20 的 SDK SQLite 方向强迫原生记录争写 SDK 库。

**取舍：**保存与恢复输入不被 Agent 引擎故障拖住；代价是原生与核心／SDK 间存在明确的交接和核验，而不是一次跨库事务。

### Q30：编辑期间准备附件，投递前固定本次实际输入

**已确认：编辑期间逐步准备必要的图片／文本等输入表示；交给 SDK 前，固定并持久保存本次实际要使用的内容关联，不在重试时无声重读改变后的原件。**

- 编辑阶段的默认准备是本地读取／转换，不因草稿预处理自动把未发送内容交给云端模型，也不自动启动会话工作。保存不依赖 Agent JS 不等于所有格式转换都已可独立完成。
- 不要求选择文件的一瞬间完整复制原件，也不承诺原件捕获是全文件原子快照。固定的是实际成功采用的表示。
- 已采用表示不得因来源变化被替换。准备尚未完整时，可以保存“准备未完成”的发送意图，但不能宣称完整内容已经接纳；无法确认原来源仍满足既定预期时明确恢复失败或要求重新选择／发送。
- 若本次仅提供资源引用说明，应明确模型尚未读到文件正文，不能把引用或缩略图冒充完整内容。实际读取后进入模型的内容也须遵守 Q16。
- 图片缩放、文本片段等必须有明确表示与范围。超过实际输入／准备预算时明确拒绝或指出可选缩减，不静默丢弃正文；不把模型输入预算误当成所有原文件都只能小于同一个大小。
- 数值上限、格式支持、物料化实现和文件清理随后依据 Provider／设备能力确定，不让用户凭空选一个 MB 数。

**取舍：**减少发送前长时间阻塞，保留稳定重试依据，并避免默认归档全部原件；代价是需要明确准备状态、容量限制及来源变化的失败处理。

### Q31：在 SDK 接纳时固定位置，使用中拒绝更改关联

**已确认：通过 SDK 接纳事务核验并保存工作位置绑定；有尚未结算的已接纳输入、相关未结束工作或未决受管效果仍使用该绑定时，拒绝修改该会话的项目关联及正在使用的共享项目／工作区位置。**

- 这是首版保守的配置前置条件，不是另建一个按输入驱动的 SDK 调度器。自动后继 run、追加输入继续使用该绑定，不假定存在通用 run-start hook。
- 忙时修改动作明确返回不可更改，不悄悄保存为待生效的新位置，也不额外建立跨位置输入队列；需要另一位置可另开会话并关联另一可用工作区的项目；正常文件操作仍可显式访问其他合法位置，工作区不是沙箱。
- 尚未确认接纳的发送保留其已知位置预期。接纳时发现配置已变，明确报告不一致，不把旧输入悄悄送到新目录；同次重试不能建立新的绑定。
- 所有受支持的主动接纳路径都必须执行同一政策，包括 Agent／扩展转交；SDK 没有通用 admission 校验 hook，不能只验证 UI 入口。
- 内部 task conversation 显式继承绑定，不自动登记成产品会话；它们后续收到输入时也不能丢失原绑定。
- 判断“仍在使用”须包含尚未结算的输入、仍可执行的相关后台任务及后代、共享记录在其他会话中的活动使用、未决受管执行，以及仍可能投递的待确认发送意图的位置预期；不能只看一个 idle 标记。已结算输入与仅用于历史追溯的保留记录，不因仍存于数据库就永久占用绑定。
- 未决效果可能使配置修改长期被拒绝；它不是自动排队的修改。条件解除后若仍需修改，用户或原调用者重新发起该配置修改动作；不能为方便而伪造工作完成。
- 具体绑定身份、相关任务集合、释放与恢复算法在 Interface／生命周期层落实；此决定不冻结原件内容、外部目录移动、系统授权或其他应用操作，且并发正确性尚未验证。

**取舍：**不用构造隐含的跨 run 位置交接，优先防止队列在错误位置执行；代价是首版不能在相关工作未结束时随意更改该会话或共享位置配置。

### Q32：用 Keystore 保护凭据密文，而非明文保存 API Key

**已确认：Keystore 保存保护密钥，API Key 密文存入应用私有 CE 存储；保护密钥丢失／失效时明确要求重新配置凭据，不静默降级为明文。**

- 不是把任意 API Key 字符串直接作为可取回的 Keystore 条目。具体加密算法、密文格式、封装库和实际硬件等级另行验证。
- 临时未解锁／暂不可用、永久失效、密文损坏与格式不兼容要分别报告；不自动删除历史或新草稿，也不把新建同名密钥说成恢复了旧密文。
- 合法模型调用仍会在请求进程内使用明文。此机制不隔离同 UID 的可信进程或随包扩展，也不代替请求选项、错误与日志的防泄漏处理。
- 当前解锁／每次认证条件由 Q33 独立确认；本题自身不隐含后台可用性，也不新增可移植密码保险箱或凭据导出功能。

**取舍：**避免将应用管理的 API Key 直接明文落盘，并利用平台密钥保护；代价是设备／安装绑定和密钥丢失后的重新配置，不能仅靠复制密文完成迁移。

### Q33：首次解锁后允许锁屏后台使用模型凭据

**已确认：为满足后台续跑，保护密钥不额外要求每次／近期用户认证，也不要求当前设备必须保持解锁；重启后仍等待首次解锁、私有数据可用且系统允许运行。**

- 这是独立的安全／可用性取舍，不由 YOLO 自动决定。YOLO 不取消 Android 授权或系统强制认证，也不绕过系统运行限制。
- 代价是当前获授权的应用在锁屏后仍能使用密钥，不提供“每次调用都证明用户在场”的保护。
- 将来若改变为更强认证条件，须重新评估后台体验并如实把相关模型调用置于等待状态，不能提前缓存明文来同时宣称锁屏封锁与无限后台使用；首版不新增此选择入口。
- 不因此新增 Direct Boot 模型执行；不把“屏幕点亮”“首次解锁完成”“当前 Keyguard 解锁”和“应用可后台启动”混为一个状态。

**取舍：**优先维持锁屏时自动工作；放弃附加的逐次用户在场保护，真实系统行为仍需目标 ROM 验证。

### Q34：首版私有工作数据不参加系统自动备份／迁移

**已确认：会话／执行数据、业务元数据、草稿、发送意图、输入内容、原生控制记录与凭据等私有工作数据，首版排除系统自动云备份和设备间迁移。**

- 当前安装内“不自动过期”不是备份。卸载、清除应用数据、丢机或换机后，不承诺自动恢复这些数据；应用升级保留本地数据与卸载重装不同。
- 这样避免将旧发送意图、停止记录和 SDK 快照混合恢复为新的可执行工作，也避免只有密文却没有原密钥的假恢复。
- 不能只设置 `allowBackup=false` 就声称成功；具体位置、云／D2D／新增通道的排除与厂商迁移行为需要按实际布局和设备验证。
- 规则只约束本应用支持的系统备份接入，不控制外部 Termux、用户原件、root 提取或任意厂商工具。没有绝对“数据不可能离机”的承诺。
- 不隐含新增导出、云同步或跨设备恢复功能；以后若需要，须另行设计一致性与恢复资格。原生 SQLite／DataStore 的选择不改变本题的数据政策。

**取舍：**首版减少不一致恢复及秘密迁移风险；代价是没有系统自动换机恢复，长期数据保护不能误以为已由本应用提供。

### Q35：首版不承诺单会话历史的物理删除

**已确认：单个会话的持久历史彻底删除暂不列为首版交付门槛；不把隐藏、撤回输入、清空模型上下文或退休 document 冒充这项能力。**

- 固定 SDK 没有相应公开删除 Interface，且 fork／结果／上下文等可以引用原记录。若用户要求首版交付，应先明确受支持的 SDK 扩展或独立安全回收方案，再评估范围，不直接绕过 SDK 改内部表。
- 本题已决定延后物理删除，不自动增加归档、隐藏页面或新的产品中心。若以后提供隐藏，必须明确历史仍保留，而且隐藏本身不等于停止执行。
- 不影响 Agent 按用户请求操作可用原文件，也不把删除产品记录联动为删除工作区文件。
- Q26 的必要内容保留继续有效；应用自有、可证明无引用的临时材料仍可按后续清理规则回收。本题不承诺 SQLite 文件中的所有旧字节可被安全擦除。

**取舍：**避免为了删除功能立即承担 SDK 持久图改造与完整引用回收；代价是首版不提供单会话彻底清除历史的能力，而不是用一个误导性的删除按钮替代。

## 6. 后续自主细化与验证边界

以下是落实已确认政策的设计工作，不是下一轮用户问卷。新增实现决定应明确标为代理自主细化；运行时、并发、存储耐久性及设备兼容保持待验证，不因完成 spec 或工单而视为已通过。当前不执行生产实现、安装或设备实验。

- 按选择落实具体 app document 的 scope／history／fork 行为和必要字段；不新增产品分支功能，不让内部 fork 复制用户发送意图。
- 按已确认的原生记录归属选择后端、事务、草稿清空／丢弃时点、内容文件布局、可重建投影与引用保护；SDK 与原生存储仍无自动跨库事务。
- 连接停用、账户变化、凭据替换及旧请求恢复的精确规则；必要旧定义不能仅因当前界面未显示就提前清理。
- 在已有输入／工作位置政策下定义 binding 身份、接纳幂等检查、相关任务与外部效果、释放与异常核验；不以 SDK generation taskId 冒充稳定工作组 ID。
- 迁移／版本错误须可见并保留原数据，不静默清空重建。何时允许只读查看、怎样恢复迁移、是否保留本地迁移保护副本，依具体存储设计落实，不混称为系统云备份。
- 数值容量预算、输入表示格式、物料化细节和故障分类需要实际依赖与目标运行时依据；目前不做安装或设备实验。
- 最后进入通信确认、订阅、重连与完整停止／恢复流程；不把数据结构清单当作这些契约已经设计完成。
