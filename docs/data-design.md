### SDK 不是空壳，也不是完整产品数据库

SDK 已保存 `ConversationRecord`、不可变 `EntryRecord`、`SubmissionRecord`、内部任务和版本化 document。它支持宿主添加 entry／document，并能在受支持的事务中提交相关修改。

但 SDK 不自动提供产品标题、项目关联、默认工作区、原始文件授权或应用配置语义。应用拥有这些语义；Q19 已确认普通业务元数据优先复用 SDK document／必要 entry，不另建一份竞争的消息正文权威库，但不把全部应用数据都放入 SDK document。

- 一个 SDK entry 可以包含多个模型消息，也可以只有应用展示数据；不能直接规定“一个 entry 就是一个聊天气泡”。
- 历史记录不等于当前模型上下文。压缩、fork 与 context edits 会改变上下文的解释，UI 不能自行拼出另一份恢复权威。
- `pi.inbox` 中的已接纳输入、`pi.live` 中的运行控制、Provider 会话身份和部分用量是权威数据；不是任意可删缓存。
- 流式 partial、watch 通知和 UI 更新不是完整的持久事件日志。可见进度可能尚未落盘。

## 2. 必须区分的数据状态与权威

这些区分来自既定职责和 SDK 契约，不作为让用户选择错误语义的投票题；具体字段与提交协议仍待设计。

| 数据 | 权威与限制 |
|---|---|
| 未发送草稿 | 用户尚未提交的输入；不能因恢复或界面重建自动发送。文字、附件草稿记录及必要内容的持有关系由原生侧独立保存；附件保留引用及必要的已生成内容，重开仍需核验可用性 |
| 用户已发起、尚未确认接纳的提交 | Q25、Q29 已确认由原生侧独立持久保存发送意图、固定内容关联和稳定身份；不能当成未发送草稿，也不能只因 UI 已显示就当成 SDK 已接纳；具体存储与回执仍须落实 |
| SDK 已接纳的输入 | 可能尚在 `pi.inbox`，未进入 transcript；接纳记录、请求身份与 entry 身份不能混用 |
| 已提交的 SDK 历史、任务与控制 document | SDK 恢复权威；通过 SDK Interface 维护，不由 UI 或 Kotlin 改内部表制造结果 |
| 用户设置、项目关联、不可重建的标题等应用事实 | 应用语义权威；Q19 已确认普通业务记录优先复用 SDK 自定义 document／必要 entry，具体作用域与布局仍待设计 |
| Android 当前授权、网络与进程事实 | 以平台实际状态为准，不能用持久化的“已授权”布尔值代替当前检查 |
| 用户停止意图与必要原生控制记录 | 必须有不依赖 JS 正常响应的控制路径；其持久记录与 SDK 协调仍待设计 |
| Termux／原生文件执行的接纳、停止确认与结果 | 工具环境执行事实；SDK 终态、SDK 提交收据不能代替外部效果核验 |
| UI 列表、分页、搜索或文件变更摘要 | 仅在有完整输入时才能称为可重建投影；不承诺掌握全文件系统变化或保留全部原始输出 |

SDK 的每个存储 batch 可以原子提交，不代表 Android 平台动作、原生控制记录和 Termux 副作用处于同一事务。

### Q13：产品会话与 SDK conversation 一一关联（已确认）

**每个已创建的产品会话关联一个 SDK conversation，持续承接该会话的多轮消息与恢复；不为每次发送或每次重启另造 SDK conversation。**

- 产品会话列表只展示应用明确登记为产品会话的记录。SDK 内部任务使用的 conversation 不自动变成首页条目。
- 这一关系不规定产品 ID 必须等于 SDK ID，也不规定消息、提交、entry 或任务之间一一对应。
- SDK 支持 fork 不等于首版新增分支聊天界面；将来若需要产品分支，会显式登记新的产品会话。

**取舍：**直接复用 SDK 的历史、上下文和恢复关联，减少多段 SDK 会话的拼接。代价是长期产品会话与 SDK conversation 的生命周期关联更紧，需要明确产品可见性、保留和删除规则。

### Q14：全部会话共用一个 SDK 逻辑存储域（已确认）

**全部产品会话共用同一个 SDK Storage，同一时刻由一个活动的 SDK Session 拥有其写入，而不是按会话或项目分别建立独立 SDK 存储域。**

- SDK `Session` 在这里指存储修改线的所有者，不是产品中的会话，也不是 Provider 的远程会话身份。进程重启后可以创建新的 Session 实例恢复同一 Storage，不要求内存实例永久存活。
- 延续既定的唯一写入所有者，不让 UI 或多个进程争写；共享存储不混合不同会话的模型上下文、消息或执行状态。
- 逻辑共享不等于一个物理文件，也不选择 SQLite、JSONL、存储驱动或事务内字段。不同会话仍可按各自条件执行，文件写入协调另按工作区规则进行。
- 原生紧急控制、凭据、Termux 账本与大文件内容不因这个选择全部塞入 SDK 存储；也不承诺跨这些来源的原子事务。

**取舍：**便于全局会话查询、路由与共享业务数据接入，减少多个 SDK 存储的目录、协调和迁移管理。代价是 SDK 数据故障与迁移的影响面更集中，仍需容量、损坏处理和恢复验证。

**后续依赖：**共享域由本题确认；普通元数据复用 SDK 和 SQLite 后端方向随后分别由 Q19、Q20 确认。哪些修改需要共同提交仍待细化，不追溯为 Q14 的隐含选择。

### Q15：工作区有稳定记录，而不只是散落的 cwd 字符串（已确认）

**工作区用稳定的内部记录表达，项目和会话引用它；实际目录位置及访问方式与记录身份分开。**

- 未关联项目的会话仍使用同一个默认工作区；关联项目的会话按既定项目关系解析工作区，不自动新增会话级目录覆盖功能，也不自动建每会话私有目录。
- 多个项目或会话可以使用同一实际目录；不能因为记录 ID、目录别名或引用来源不同，就当作互不冲突的可写位置。
- 稳定记录不是新增产品中心，不把工作区改成安全沙箱，也不替代系统授权。
- 记录身份、执行环境身份、目录定位和访问能力不是同一个值。路径／URI 映射、位置重绑和无法确认的别名仍需明确核验，不能承诺任意 SAF URI 都可等价为 POSIX 路径。
- 不在本题锁定目录重叠、跨工作区写入、未知写范围的完整调度规则，也不把应用锁说成能阻止其他应用或手工 Termux 操作。

**取舍：**减少项目、会话和执行记录之间重复保存目录字符串，便于保留共享关系。代价是维护位置与引用的核验规则，不能用增加一个 ID 来假装解决所有文件别名问题。

### Q16：附件输入版本与原始文件引用分开（已确认）

**记录本次作为模型输入采用的稳定内容版本，并另记可用的原始资源引用；原文件后续变化不应改写当时已经采用的输入内容。**

- 固定的是实际输入表示，例如选定的图片表示、提取文本或已读取片段；不是默认完整归档每个原文件，也不是要求把所有二进制放进 SDK JSON。
- 来源可以变化、被移动、删除或撤销授权；内容版本的存在不保证原件仍能访问。
- 对原文件的修改仍要针对实际原件执行并核验；改了输入副本不能报告为原文件已修改。
- 输入内容版本不是“精确 Provider 网络报文”的保证；SDK hooks、模型上下文处理或 Provider 编码仍可能改变最终请求。
- Q30 后续已确认编辑期间逐步准备输入，投递 SDK 前固定并持久保存实际采用的内容关联。具体物料化、大小限制、清理与授权处理继续细化，不承诺选择文件这一瞬间就完成全文件原子快照。

**取舍：**历史与恢复不依赖原件恰好仍保持旧内容，但会增加必要的内容留存、引用与清理成本。只保存当前路径并在以后重新读取更省存储，却可能让同一次输入的内容无声变化。

### Q17：共享模型配置，每个会话保留自己的模型选择（已确认）

**Provider 配置和凭据统一管理，设置一个新会话默认模型；新会话初始化自己的模型选择，此后各会话独立保留。首版不另加项目级模型继承层。**

- 修改新会话默认模型，不自动切换既有会话；在某会话改模型，不改变其他会话的选择。
- 初始化的是模型选择／引用，不是把 API Key 复制到每个会话。鉴权仍由模型配置 Module 在请求时使用 SDK `Models`／`CredentialStore` 接入。
- Q28 后续已确认目的地或不兼容协议变化采用新连接身份，保留仍被引用的旧定义，不静默改投新服务。凭据轮转、账户变化与旧响应兼容细节继续落实；不把旧密钥保存到请求检查点。
- 不增加项目级模型覆盖，只约束模型选择的继承层数，不决定项目所有其他上下文能力。
- 默认模型不存在、被删除或不兼容时要给出明确状态，不因此默许静默换成另一模型；具体流程仍待设计。

**取舍：**减少重复配置，同时避免修改全局默认值意外影响老会话。代价是既有会话不会自动跟随默认值变化，首版也不提供项目级模型继承便利。

### Q18：首版文字草稿耐久性（已确认新增范围）

**首版保存每个会话尚未发送的文字草稿，重开应用后恢复已保存内容，但绝不自动发送。**

- 用户已明确接受这一相对原型内存保持方式新增的产品范围；它不是此前“执行自动续跑”自动包含的能力。
- 草稿与已发起提交、SDK 已接纳输入、持久历史分别建模，不能用一个“消息已保存”状态混淆。
- 本题只选择文字草稿是否跨应用重启保留，不选择存储位置、刷盘频率或每次按键零丢失保证；不因本题要求 UI 直接写 SDK 数据库。
- 附件草稿后来已由 Q24 单独确认：保留引用及必要的已生成内容，失效时提示重新选择；不完整备份全部未发送原件。具体布局与清理仍待设计。

**取舍：**减少手机应用重建后丢失长输入的风险，但需要保存失败、清空、会话切换和丢弃策略。该草稿不会成为新任务或自动运行来源。

## 4. SDK 数据政策事实

[数据政策专项核查](research/pi-sdk-1.5-data-policy.md)已完成。以下是固定源码事实与其限制，不是新的产品选择：

- SDK `session` document 是跨进程重开仍保留的共享数据，不是进程内缓存。conversation document 的 `latest`／`rewindable`、fork 的 `current`／`asOf`／`initial` 是不同语义；值迁移不能改变已有实例的这些规则。
- 应用可以在创建 SDK conversation 的事务内登记产品关联、初始化 document 与模型选择；首次提交输入仍是另一个操作。全局创建 hook 也会遇到内部 SDK conversation，不能全部登记进产品列表。
- `Harness.open()` 会做恢复写入，但尚不调度任务。Models／settings getter 是同步 Interface，settings 回调可能在 open 期间就被读取，因此此前必须已有安全且语义有效的同步启动值，不能引用尚未初始化的 Harness。完整业务配置就绪后才能允许调度；不能在 getter 内临时异步读库或重入 SDK 修改线。`submit()`、`abort()`、等待调用等也能启动调度，不能只拦 `resume()`。
- 应用新会话默认模型需要在创建时显式写入；SDK 没有自动承接应用默认模型的 `HarnessSettings.model` 字段。
- **模型切换不能概括为“有检查点就永远沿用旧模型”。** 新 generation 的每次 prepare 解析当前选择；普通失败重试与崩溃恢复后的新尝试可以重新 prepare。正常 close 后恢复原请求、已有 deferred handle 的轮询、已选择请求的 compaction 则保留原模型引用。
- 模型引用不冻结 Provider 端点、模型定义或凭据；请求时还会解析当前 Models 和鉴权。保留旧引用不等于安全保存了完整旧连接配置；宿主按已确认 Q28 保留必要旧定义，并核验凭据、鉴权端点与旧响应兼容性。
- SDK 的工具环境在使用时解析。已开始工作若需固定项目／工作区位置，由宿主明确记录和落实，稳定工作区 ID 自身不会固定目录绑定。
- SDK 图片模型输入要求内联 base64，没有通用文件／blob 引用替代。应用可保存原件引用和必要文件内容，但不能透明地把 SDK 的图片字段换成路径或 URI；具体体积与内容布局要遵守真实 SDK 契约。

### Q19：普通应用业务元数据复用 SDK document／entry（已确认）

**标题、产品会话登记、项目／工作区关联、普通会话设置和适合该生命周期的扩展业务状态，优先用应用自定义的 SDK document／必要 entry 保存，不另建一套竞争的主业务数据权威。**

- 应用拥有这些记录的语义和版本；SDK 提供实际持久化与受支持的共同提交，不替应用定义项目和工作区。
- 凭据、原生紧急控制、草稿、尚未交给 SDK 的投递记录、Termux 执行事实和独立大文件内容，不随本题一并塞入 SDK document。它们的位置另按职责与可靠性决定。
- 不复制已有消息正文作为另一份权威。可重建的列表或索引不是第二套消息历史。
- 全局共享记录、会话状态及其 fork／rewind 行为在下一层逐项明确；不把每个项目复制到各个会话，也不将任意记录默认设为 rewindable。
- 初始化需遵守上节的同步 getter、启动配置就绪和事务约束；SDK 支持 document 不等于这些接线已经实现。

**取舍：**减少双写、跨存储协调与重复消息模型，部分关联可与会话创建共同提交；代价是更依赖 SDK 的作用域、迁移与读取契约。独立应用数据库仍是被比较的替代，不因本题直接选引擎。

### Q20：SDK 主存储先以 SQLite 为设计目标（已确认）

**共享 SDK Storage 先按 SQLite 后端设计，复用 SDK 已有 SQLite Adapter，不以 JSONL 或内存作为首版主存储方案。**

- 这是后端方向，不是生产驱动已选或 Android 验证已通过。Node 内置或原生桥接驱动仍须随实际运行时验证。
- 必须满足 `STRICT`、`json_valid`、`runCounted()`、事务隔离、批次提交和耐久收据等真实 SDK 契约；不能删除约束或用不正确的行数结果凑接线。
- 不要求原生草稿、控制记录或凭据与 SDK 共用同一数据库／连接；共享一个 SDK Storage 也不意味着整个应用只有一个文件。
- 目前没有安装、建库或运行任何存储测试；JSONL 等保留为比较或后续交换能力，不据此新增导入导出交付。

**取舍：**利用 SDK 的查询、索引和事务实现，适合多会话持久记录；代价是驱动与原生库兼容、迁移、故障和耐久性都要验收。若目标运行时无法满足契约，应复审，而非假装已经兼容。

### Q21：已开始的工作不随项目修改悄悄换位置（已确认）

**保存已开始工作实际采用的项目／工作区位置绑定版本，项目关联或目录配置的后来修改不让它途中改到另一个位置。**

- 固定的是执行使用的关联和位置依据，不是工作区文件内容、系统授权或整个文件系统快照。原件移动、删除或访问失效仍须核验。
- 这是宿主补充的执行上下文事实，不复制 SDK 的任务状态机；SDK 本身会在使用环境时读取 cwd，不能误称已自动提供整段工作的冻结。
- 默认工作区仍不是安全沙箱；此规则不禁止命令显式使用其他合法目录或操作授权原文件。
- Q31 后续已确认在 SDK 接纳事务中核验并保存位置绑定，覆盖排队输入、追加输入、自动后继工作及内部会话继承；使用中拒绝修改会话关联和正在使用的共享位置，不排队保存待生效修改。具体分组、引用核验与释放算法由后续设计落实。
- 系统授权、省流、停止和真实资源可用性仍按当前事实检查，不沿用快照里的旧许可。

**取舍：**防止长时间执行或恢复后突然在错误目录操作；代价是保留可核验的位置版本，并按 Q31 在使用期间明确拒绝关联或位置修改。

### Q22：模型选择更改沿用 SDK 的逐尝试生效规则（已确认）

**会话改模型后，后续新准备的生成尝试使用新选择；不为这次设置修改强行取消或重发已发出的请求，恢复与压缩沿 SDK 原有规则处理。**

- 工具回合后的新生成，以及普通自动重试、崩溃恢复后重新 prepare 的尝试，可以使用新选择。不能承诺“同一次用户请求从头到尾永远只用旧模型”。
- 已准备或在途的请求不会因配置修改被中途替换；正常 close 成功后恢复原请求时保留其 checkpoint 模型引用。
- deferred handle 的轮询继续查询原响应；已选定的 compaction 请求重试仍使用原模型引用，不另造一套模型切换状态机。
- 模型选择与 Provider 连接设置、模型定义、凭据是不同的数据。本题只选择模型切换政策，必要旧连接定义由后续确认的 Q28 保留；不把旧 Key 写进检查点，停用、账户变化及凭据轮转的兼容规则继续落实。
- 不因模型切换新增逐请求操作审批，也不承诺无重复模型计费。

**取舍：**及时使用新的会话选择，同时最大程度复用 SDK；代价是一次较长工作中可能使用多个模型，普通重试与继续旧响应的行为需要明确呈现。

### Q23：未发送文字草稿由原生侧独立持久化（已确认）

**文字草稿通过应用 Interface 交给原生侧持久保存，不以 Agent JavaScript 已启动或正常响应为保存前提。**

- React 继续负责编辑和局部输入状态；原生侧保存草稿值。SDK 已接纳的输入、会话历史和执行状态仍由核心／SDK 管理。
- 未发送的草稿属于 UI 输入态，不因此把业务协调或 SDK 数据所有权迁到 Kotlin。
- 不选择具体原生数据库、文件格式或刷盘周期；“恢复已保存内容”不等于每次按键都同步持久或系统硬故障下绝不丢字。
- 保存失败要可见，不能仅因 UI 内存已有文字就显示持久保存成功；接口与确认细节后续设计。

**取舍：**降低启动、运行故障和 UI 重建对长输入的影响；代价是协调独立草稿记录、会话引用与版本，不能让迟到的保存／清空覆盖新编辑内容。

### Q24：附件草稿保留引用与已物料化内容（已确认新增范围）

**首版也恢复草稿中已选附件的引用及必要的已生成内容，重开时重新核验可用性；不为每个未发送附件默认完整复制原件。**

- 这是 Q18 之外新增的附件草稿范围，现已单独确认，不是先前文字草稿决定的隐含范围。
- 可用的持久来源引用和已生成的必要输入表示可以恢复；平台不支持持续访问、原件消失或授权失效时，明确标为不可用并让用户重新选择，不伪装已经恢复完整附件。
- 预览缩略图不一定足以作为原定模型输入；不能在缺少原内容时无声拿缩略图替代。
- 已生成内容若是恢复输入的唯一来源，就不能同时把它当作随意可删缓存。所有者、引用与清理方式在后续布局中确定。
- 本题不决定是否由与文字草稿相同的物理存储承载，也不承诺所有临时 URI 都能持久授权。

**取舍：**减少重开后重新整理附件的工作，同时避免无条件复制大文件；代价是处理引用失效和局部恢复，不能保证外部来源永久可用。

### Q25：已发起但未确认接纳的发送意图单独持久保存（已确认）

**用户点发送后，保存独立于草稿的发送意图、固定内容关联和稳定提交身份；中断后核验或重试同一次提交，而不是丢失它或把它当成一次新发送。**

- 文字草稿不自动发送；发送意图必须源于明确的发送动作。它尚未得到 SDK 接纳确认时，不能显示为已经完成 SDK 接纳。
- 重试同一发送保持目标会话、内容版本与身份；用户主动再发一次，即使文字相同，也不是按内容去重的同一意图。
- SDK 已接纳后，由 SDK 的 submission／inbox／entries 承接相应权威；投递记录不成为另一套 Agent 任务队列或产品任务中心。
- 先前保存的发送内容与用户随后继续编辑的草稿分开，不能重试时读取最新草稿，或用迟到确认清空新草稿。
- 恢复投递仍须遵守用户停止、已撤销／取消意图和系统运行条件；完整停止作用域后续明确，不借自动投递复活应当停止的工作。
- 不承诺物理点击瞬间就耐久、不选择回执与重连协议，也不把提交去重说成外部效果恰好一次或模型零重复计费。

**取舍：**减少进程退出造成的已发输入丢失和重连重复提交；代价是维护待确认投递、SDK 接纳结果与草稿之间的核验关系。

### Q26：正式历史及仍需引用的输入内容默认不自动过期（已确认）

**已持久化的正式会话历史和仍被有效输入引用的必要内容不按时间自动淘汰；可重建缓存可以回收，空间不足或保存失败要明确呈现。**

- 压缩模型上下文不等于删除原历史。不可重建的输入内容不能仅因体积大就被标为缓存。
- 这不是无限容量保证，也不增加完整原文件备份或永久保存全部 stdout／调试日志的承诺。草稿材料、执行核验记录与运行日志各自的生命周期继续按引用和用途定义。
- SDK inbox、live 控制、Provider 身份和必要用量不是普通 UI 缓存；SDK 自身 task memo 的终态退休等契约也不会因此被改成永久保留。
- 不默默删除原文件、工作区内容或仍需核验的唯一证据来腾空间；实际清理算法、阈值和具体保留记录另行设计。本题约束应用自动清理，不禁止 Agent 按用户请求执行正常的授权文件操作。
- Q35 后续已确认首版不以单会话历史物理删除为门槛，不用隐藏或退休 document 冒充删除；Q34 确认私有工作数据排除系统自动云备份／设备迁移。其他显式删除语义与引用分析继续按实际范围设计，不自动新增删除 UI、归档或云同步功能。

**取舍：**让历史和恢复依据更可预期，避免用户未要求的数据过期；代价是长期空间增长，需要容量提示和明确的后续删除／清理规则。

## 6. 已确认的 Q27—Q35 与后续细化

Q13—Q35 已确认；记录职责与完整取舍集中在[应用记录设计](data-records.md)。用户于 2026-11-03 接受 Q27—Q35 全部推荐，不再逐项询问普通技术细节：

- Q27：普通应用元数据按当前值组织，不新增完整编辑审计；必要投递／执行版本另留。
- Q28：目的地或不兼容协议变化使用新的模型连接身份，不静默覆盖旧请求引用。
- Q29：附件草稿与未确认发送意图也由原生侧独立持久化。
- Q30：编辑期间准备附件，交 SDK 前固定本次实际输入表示，来源变化与超预算明确处理。
- Q31：SDK 接纳时核验并固定位置；未结算输入、仍可执行的相关任务或未决效果仍使用时，拒绝改会话关联及共享位置配置，不自动排队修改。
- Q32：Keystore 保护加密密钥，私有 CE 存储保存 API Key 密文；密钥失效不降级明文。
- Q33：首次解锁后不额外要求每次认证或当前保持解锁，以支持锁屏后台工作。
- Q34：首版私有工作数据排除系统自动云备份与设备迁移，不承诺换机恢复。
- Q35：单会话历史物理删除暂不作为首版门槛，不以隐藏冒充删除，也不自动新增归档功能。

[SDK 输入与退休核查](research/pi-sdk-1.5-input-and-retirement.md)已确认没有通用 run-start hook，也没有公开会话历史删除 Interface；[Android 私有数据研究](research/android-private-data-and-backup.md)区分了 CE、Keystore、认证与备份条件。研究不等于实现或设备验收。

随后由代理自主收敛以下设计，并区分自主设计与仍需运行验证的事实；只有改变已接受承诺、路线不可行、发布目标缺失或需要新的执行授权时集中确认：

- 普通应用 document 的作用域、共享引用、fork／rewind／保留政策，创建与首次提交的关联，以及类型化迁移和启动投影的就绪门槛。
- 按已确认的 SDK 接纳绑定时点落实执行上下文分组、忙时拒绝修改和引用释放；按新连接身份政策落实 Provider 停用、凭据轮转与现有请求／deferred handle 的兼容处理。
- 草稿、发送意图、SDK submission／entry、附件及执行事实的字段与关联；必要内容的物料化、大小限制、实际布局和清理。
- 原生停止意图与 SDK 状态、工具环境账本的协调；按 Q32—Q34 落实 Keystore 保护、凭据异常分类、锁屏可用性与备份排除，不重新询问这些政策。
- 类型化迁移、引用保护与允许回收的材料；单会话历史物理删除不作为首版门槛，不能把仍被引用的记录视作无主缓存，也不以本地迁移保护副本冒充系统备份能力。
- 通信层确定接纳确认、重复提交、断线重连、状态订阅和版本；生命周期层验证回收、停止、未知效果、重试与锁释放。SDK 提交收据仍不等于外部执行收据。
