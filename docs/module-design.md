# Module 设计：应用协调与 Android 机制

状态：Q8—Q12 均已由用户确认，Module 职责与扩展登记方向已收敛；进入领域模型与持久化讨论，不是实现授权。用户特别要求区分 Android 系统授权与首版 YOLO 不实现的操作审批。接口形状、持久化布局和通信协议尚未冻结。

## 已确定的输入

- UI 为 WebView 中的 TypeScript／React；Kotlin 承接 Android。
- Android Service 管理与 UI 宿主分开的本应用运行进程；主 Agent 与 Pi Durable／Pi AI `1.5.0` 不进入外部 Termux。
- 独立官方 Termux 提供完整工具环境，正常使用最多只在首次初始化需要人工操作。
- 本应用先以 `compileSdk=36`／`targetSdk=36` 验证。首版按 Android 16 起、ARM64 设计，平板布局与功能保留。
- Javet Android Node 是首个验证候选；SDK 加载、存储、网络、停止与恢复尚未通过运行验证。以下设计不将候选冒充已验证能力，也不预建万能多引擎框架。
- 会话、项目、工作区与扩展的产品含义沿用 `GLOSSARY.md`。Module 不等同于产品实体、进程、语言目录或独立产品任务。
- Q13、Q14 已确认产品会话与 SDK conversation 一一关联，全部产品会话共用同一 SDK Storage，同一时刻由一个活动 SDK Session 拥有写入，见 [ADR 0007](adr/0007-shared-sdk-storage-for-conversations.md)。不是每个产品会话各开一个 SDK Session 争写。
- Q15—Q18 已确认稳定工作区记录、附件输入版本与原件引用分开、共享配置而模型选择逐会话保留，以及文字草稿耐久性；Q19—Q35 后来也已确认；具体字段、布局与 Interface 由代理在首版 spec 收敛。
- Q19、Q20 确认普通业务元数据复用 SDK、SDK 主存储以 SQLite 为目标，见 [ADR 0008](adr/0008-sdk-documents-and-sqlite.md)。Q23 确认原生侧独立保存未发送文字；附件草稿与未确认发送意图的持久范围已定，其具体归属与存储继续设计。

## 已确认：Q8 业务协调的主语言与职责

**用户已确认：应用业务协调主要放在 TypeScript 核心，Kotlin 负责 Android 机制与不依赖 JS 响应的控制。**

决策记录见 [ADR 0006](adr/0006-typescript-core-with-native-control.md)。主 Agent 所在应用与 UI 不持有执行状态仍沿用既定选择；本题确认了业务规则的主侧，避免 TypeScript 与 Kotlin 各自维护一套会话状态机。

### 已确认的职责方向

| 位置 | 负责方向 | 不负责 |
|---|---|---|
| 应用自有 TypeScript 核心 | 会话协调、项目／工作区上下文、应用策略、SDK 集成、应用领域记录的组织、执行事实的业务解释与扩展逻辑 | 不重写 Pi Durable 的执行／恢复状态机；不假定自己能绕过 Android 生命周期或凭空判断外部命令完成 |
| Kotlin Android 宿主 | 运行进程及 Service 生命周期、系统授权与网络等平台事实、原生能力接入、启动／唤醒机制、JS 无响应时的紧急控制 | 不复制模型协议、会话调度或 SDK 检查点；不把进程退出直接写成会话完成或停止成功 |
| React UI 与界面扩展 | 呈现、输入、局部交互，以及通过应用 Interface 发出动作和观察状态 | 不直接控制 Termux，不直接写 SDK 数据库，不在页面生命周期里恢复 Agent |

应用领域记录由核心组织，不等于所有数据必须由 JavaScript 直接落盘。存储驱动可以通过 Adapter 提供；SDK 数据仍须有单一写入所有者。Android 的系统授权事实与必要控制记录另有明确归属，不与 SDK 数据库争写。

### 系统授权、操作审批与其他执行条件

用户已明确：**首版 YOLO 不实现操作审批，但系统授权仍然存在。**

| 类别 | 含义与归属 | 首版行为 |
|---|---|---|
| 系统授权 | Android 对实际访问资源的应用／执行主体授予能力；Kotlin 适配申请、检查与系统结果 | 按真实系统规则处理缺失、拒绝和撤销；不能由 YOLO 代替 |
| 操作审批 | 应用额外要求用户批准某一次 Agent 动作；属于未来应用策略能力 | YOLO 不走此流程，不建设审批队列、批准弹层或空审批框架 |
| 其他执行条件 | 环境就绪、省流、用户停止、工作区排队、调用者身份与结果核验 | 继续生效；等待、拒绝或不确定结果不是“等待操作审批” |

- 区分依据是控制方和授权对象，不是弹窗次数。Android 可能对新资源或特定操作要求再次交互；首版不在系统要求之外再加逐操作批准。
- 本应用和 Termux 不共享 UID 或系统授权。按实际执行主体与资源检查，不假定一方获得授权就让另一方直接获得同样的访问权。
- `RUN_COMMAND` 的 Android 权限与 Termux 的 `allow-external-apps` 配置是不同条件；后者属于环境初始化，不是系统授予的权限，也不是逐命令审批。
- 模型凭据配置与远端鉴权又是另一类事实，不将鉴权失败误报成 Android 授权不足或等待操作审批。
- 未来命名与状态必须区分上述原因，不能用一个含混的“权限待批准”覆盖全部失败。原型中 YOLO 的含义是免操作审批，不是全部系统能力已获得授权；本轮不改变已定布局。

### 对调用者呈现一个深 Module，而不是语言转发链

应用行为的 Interface 应表达“向会话提交输入、观察会话、请求停止”等行为，并说明接纳、失败、失联与停止确认的含义。它不逐个镜像 `Harness`、Javet 或 Android 方法。

Implementation 可以跨 TypeScript 与 Kotlin。UI 不必了解内部如何创建引擎、连接执行端或提交检查点；测试从同一 Interface 观察结果。只有实际存在变化的位置才形成 Seam，例如 Android 事实和控制、外部执行以及 SDK 已提供的存储／环境接口。

这不提前选择 Interface 的方法列表、Binder／管道／套接字，也不要求每个内部职责都生成一个公开 Module。纯转发没有获得独立测试或隐藏复杂性的价值时，应留在 Implementation 内。

### 停止不是“交给 JS 再等它回答”

用一个必要场景检验分工：用户点击停止时，JS 引擎已无响应，而 Termux 中仍可能有命令运行。

- Kotlin 必须保留不依赖 JS 正常响应的平台控制能力，不能让停止入口同样永久卡住。
- 进程终止、用户停止意图、外部命令停止确认不是同一件事。
- 不能因杀掉本应用的引擎，就宣布外部 Termux 后代已经退出；无法确认时必须保留不确定状态。
- 重建运行宿主时必须尊重用户停止，不能让自动恢复把旧工作重新启动。
- 此处只分配控制职责，不选择停止意图的具体持久记录、恢复闸门或取消协议；它们在数据与生命周期层继续设计。

这个控制职责不构成另一个 Agent，也不允许 Kotlin 直接修改 SDK 的内部表来制造终止结果。

### 集中策略不等于只检查一次

省流、工作区协调等应用规则应有统一归属。平台和执行侧仍须执行实际动作所需的控制条件，并响应平台变化；不能只在首次 UI 提交或某个 `beforeTool` 中检查一次。

Pi Durable `1.5.0` 的安全重放可能跳过 `beforeTool`，而恢复模型工作也不自动恢复 Android 进程或核验 Termux 副作用。因此，最终执行路径仍需覆盖策略、停止和执行事实，不能依靠入口检查冒充完整约束。

## 为什么选择 TypeScript 为业务主侧

- Pi Durable／Pi AI 本就在 JavaScript 运行时中；SDK 接入、业务规则和扩展逻辑放近，可减少把内部对象来回翻译成 Kotlin 模型的需要。
- 可从相同应用 Interface 测试业务行为，以真实 SDK 加受控平台／执行 Adapter 组合测试；不要求所有业务测试都依赖 Android UI。
- Kotlin 保留真正需要 Android 的机制，以及引擎异常时仍可生效的控制，不沦为完全无法理解故障的转发层。

**代价：**JS 与原生之间仍需异步交互、生命周期协作和控制语义；把业务集中到 TypeScript 不会自动解决这些问题。需要限制引擎线程、跨语言对象和 SDK 实现细节向调用者泄漏。

### 实际比较的另一条路线

由 Kotlin 作为应用协调中心，TypeScript 只提供较薄的 SDK 运行接线，也可以符合“主 Agent 在本应用”。它更贴近 Android 生命周期，但需要更多跨语言业务映射，并特别防止 Kotlin 的会话状态与 SDK 状态成为竞争的权威来源。

该路线不是不可能；用户选择 TypeScript 业务主侧，是为了集中业务知识、复用 SDK 和降低重复模型成本，不是因为 Kotlin 无法承载应用逻辑。

## 已确认：Q9—Q11 的 Module 职责

用户对以下 3 项回答“都可以”。工具环境、固定核心与扩展关系、模型配置统一入口均已确认；这不选择数据库、通信协议、加密算法或操作审批流程。

### Q9：一个深工具环境 Module（已确认）

**工具面的文件访问、命令生命周期、环境就绪、输出、取消及结果核验，由一个工具环境 Module 统一承接，并通过 SDK 环境 Adapter 接入核心。**

- 调用者无需了解 Termux Intent、PID、日志目录和重连细节；不能由 UI、Bash 工具、文件工具各自维护一套 Termux 控制逻辑。
- 该 Module 报告接纳、运行、完成、停止确认和不确定结果等执行事实；会话核心依据事实与 Pi Durable 决定工作如何继续，不把会话恢复决策下放到 Termux。
- 核心的工作区协调与应用策略已有统一职责归属；工具环境接收执行上下文，落实实际执行条件，不另设一套竞争的业务策略。
- 该 Module 的 Implementation 可以跨 TypeScript、Kotlin 与 Termux；具体进程位置、客户端语言和传输仍待设计。原生紧急控制不得因需要经过无响应的 JS 才能使用此 Module 而失效。
- SDK 私有数据库、模型凭据和应用设置不是工具工作区文件。会话路由、修改应用设置等工具使用对应应用 Interface，不为“统一工具环境”而绕到 Termux 执行。

**不隐含的能力：**不会把 SAF URI 伪装成普通 shell 路径，不默认导入副本就等于修改原文件，不承诺原子外部副作用或所有后代必然停止。文件与命令需要一致的工作区语义，无法提供某种访问方式时必须明确报告能力限制。

**取舍：**把跨 UID 就绪、命令状态和文件语义集中，避免复杂性散入每个工具；代价是该 Module 要维护清晰的内部职责，而不是成为没有 Interface 约束的万能转发器。具体存储、执行收据格式和协议留待后续。

### Q10：核心机制固定，扩展通过 Interface 使用（已确认）

**持久化与恢复不变量、停止控制、平台检查和实际执行控制入口留在固定核心，不把这些机制本身作为普通扩展注册或替换。**

- 既定的内置工具、提示词能力和界面功能继续使用扩展接入机制；这不等于“每一项内核机制都是插件”。
- 扩展可以使用宿主提供的持久化能力保存自己的状态，不接管 SDK 数据库所有权、事务提交含义或恢复规则。
- SDK 支持的任务／工具协作、提示词扩展和业务执行包装仍可使用；固定的是宿主持久化与控制不变量，不是禁止 SDK 的业务扩展能力。
- 普通扩展 Interface 不提供移除停止控制、绕开系统检查或替换核心状态机的入口；不为每个扩展再创建一套运行监督与执行核验。
- “固定核心”不等于全部放在 TypeScript：Android 检查与原生紧急控制仍在 Kotlin。源码内的实现重构、测试 Adapter 与经明确设计的替换，不等同于向普通扩展开放内核接管。
- 真实自定义 UI、UI-only、可信随包扩展和不承诺旧插件原文兼容已经确定，不再投票；信任随包代码也不是对恶意扩展的安全沙箱承诺。
- 未来操作审批可在已保留的应用策略接入位置增加，首版不因“扩展性”建设审批子系统。

**取舍：**减少全插件化的启动顺序、关键依赖和故障处理成本；扩展不能通过公共接入方式任意替换核心机制。具体注册描述、生命周期与扩展间交互在此决定之后设计。

### Q11：统一模型配置与凭据入口（已确认）

**由一个应用拥有的模型配置 Module 统一承接模型配置与凭据访问，内置页面、Agent 设置能力和扩展经同一 Interface 使用；模型协议与调用继续复用 Pi AI。**

- 会话核心消费模型能力与配置，不在每处调用、每个插件里独立保存或解析一份模型配置／Key。
- 凭据能力通过平台 Adapter 接入。普通配置查询默认返回公开配置和是否已配置凭据等信息，不将原始 Key 混入常规状态广播。
- 这是职责与数据曝光面的选择，不引入每次模型调用前的批准、登录或系统授权提示，也不重建 Provider 框架。
- 当前不选择数据库、加密算法、具体 Provider 支持清单或凭据导出功能；接入层存在不等于所有 Provider 已通过 Android 验证。
- 本轮补充审计已发现请求选项复制凭据的路径，详见后文数据层准备；后续仍须验证检查点、错误、日志与广播。有原生凭据存储不等于已证明整条链路没有明文持久化，API Key 在请求期间的使用也不等于对可信核心扩展建立了进程内秘密隔离。

**取舍：**在一个位置协调 SDK 模型元数据、应用配置和原生凭据，减少分散副本与误曝光；仍需处理原生与 TypeScript 的交互，以及后续配置作用域和快照语义。

## 已确认职责形成的依赖方向

这是逻辑协作关系，不是新选定的进程、源码包或传输协议：

- UI 与 UI 扩展通过应用 Interface 查询、订阅和发出动作，不直接访问 SDK 对象、SDK 数据库或 Termux 控制入口。
- TypeScript 核心复用 Pi Durable，调用工具环境与模型配置 Module，解释执行事实并协调会话及工作区。
- Kotlin 管理 Android 机制、提供系统事实与原生能力，并保留不依赖 JS 响应的紧急控制；这些不是第二套业务状态机。
- 工具环境内部连接实际文件访问能力及 Termux 执行端；模型配置内部复用 Pi AI 和原生凭据能力。它们不因名称分别叫“环境”或“配置”就变成额外进程或 HTTP 后端。
- 依赖通过既定 Interface 在装配处提供，不为每个职责创建全局查找器或空包装层。具体入口与失败语义在后续契约中落实。

## 扩展装配的已核验事实

固定 SDK 1.5.0 的 [扩展组合审计](research/pi-sdk-1.5-extension-composition.md)已完成：

- SDK `Extension` 只有 `name` 与可选 `tools`、`sections`、`hooks`、`wraps`、`tasks`；不含 React UI、依赖清单或通用 `setup`／`dispose`。
- Agent 贡献已由 SDK registry 组合；同名扩展安装会替换，跨扩展工具／section 可按会话选择顺序覆盖，而重复任务名会失败，不能一概写成“重名总是报错”。
- UI-only 可通过现有应用查询／订阅读取核心能力，不需要空的 Agent 扩展或假工具；也不意味着完全不依赖核心查询。
- SDK 卸载扩展不会自动停止旧调用或释放资源，页面卸载不等于停止 Agent。资源所有者仍须明确，不能新增一套假定 SDK 已有的插件启停机制。
- 可选 UI＋Agent 入口的应用描述可以只做身份与构建入口关联。两侧只加载各自 Implementation，Agent 贡献仍交给 SDK；一个描述文件不能让闭包或 React 对象跨进程共享。

研究事实不自动成为选择；用户随后已通过 Q12 确认薄的应用描述方向。运行时热替换、插件依赖求解器或手机动态安装未因此加入首版范围。

## 已确认：Q12 扩展登记的关联方式

**用户回答“可以”：同一功能使用一份薄的应用扩展描述，关联可选的 React UI 入口与可选的 Agent 贡献入口，而不是分别维护两份彼此独立的功能清单。**

- 可以只有 UI、只有 Agent 贡献，或两侧都有。两侧入口各自在所属运行宿主中加载；这沿用既定的 UI-only 与后台独立要求，不是重新决定这些能力。
- UI 入口交给应用界面宿主；Agent 贡献交给已有 SDK registry。描述只关联身份与构建入口，不复制 SDK 的工具组合、hooks、包装、任务版本和恢复机制。
- 应用标识与最终装配的 SDK 扩展身份分别应明确且无意外重复；装配时将误重复报告为错误。应用标识不因此强制等于 SDK `Extension.name`。
- 身份校验不禁止 SDK 原有的跨扩展工具／section 有意覆盖；这些仍按 SDK 的选择与组合规则处理，不用一条“所有重名都禁止”取代其语义。具体诊断格式与选择控制留后续契约。
- UI-only 可以查询已有核心能力，不需要空 Agent 入口。关闭页面只结束其 UI 资源使用，不借此停止会话；描述不会让 React 组件与 SDK 闭包共享运行上下文。

**取舍：**把一个功能的两侧入口关联在一处，减少配套功能登记分散；代价是维护少量应用自己的描述与构建分发规则。另一条可行路线是两个显式清单加共享标识。本题不选择描述文件格式、字段名或一个入口可产生多少 SDK 贡献。

不新增插件依赖求解器、全局插件生命周期框架、运行时热替换或手机动态安装要求；也不改动 Q10 的固定核心机制。扩展实际依赖通过普通代码依赖与明确的宿主能力接入表达，需要额外资源时再确定其所有者。

Q12 已确认；[领域模型与持久化](data-design.md)中的 Q13—Q26 现也均已由用户确认，继续细化记录策略。基本 UI 表达能力、共享 React、UI-only、可信随包和工作区协调归属均不重复询问；UI 具体挂载位置、数据查询与交互协议结合数据模型在后续 Interface 层继续设计。

## 进入数据层前的事实准备

[SDK 数据权威审计](research/pi-sdk-1.5-data-authority.md)已完成，提供以下事实；SQLite 后端方向后来已由 Q20 确认，具体 schema 未定：

- Durable 已保存 conversation、entries、submissions、任务与 documents；不应另造一份竞争的消息正文权威，也不能假定 SDK 已自动包含产品标题、项目、工作区与附件语义。宿主可以通过其自定义 entry／document 接入。
- 不能将所有 SDK document 当缓存：inbox、live 中的运行控制、Provider 会话身份和部分用量都有权威意义；普通 UI 分页与展示投影是不同的数据。
- SDK `Models`、`CredentialStore` 和 `ModelsStore` 是真实接入位置；模型目录 store 不是整个应用设置库。
- generation／compaction 会保存请求选项。鉴权 headers 或运行时额外的 `apiKey` 可被复制进检查点；类型没有声明某字段不等于运行时会过滤它。实现时不得把应用管理的凭据塞入这些可持久化选项，应走请求时鉴权的 SDK Seam。
- 这不表示当前发生了凭据泄露，也不证明整条链路已安全。SDK 错误内容可能持久化，仍须设计适当的日志与错误处理，并验证；不增加操作审批。

### 不再重复询问与后续依赖

- **工作区协调归属已由 Q8 确认在 TypeScript 核心。** 不再单独询问是否由核心管理跨会话排队；锁范围、持久记录、中断后释放条件仍需后续设计。
- Q8—Q12 均不改变系统授权与操作审批的区分，也不是实现授权。
- Module 职责与扩展登记已收敛；[数据设计](data-design.md)中的 Q13—Q26 已确认，[应用记录设计](data-records.md)中的 Q27—Q35 也已全部确认；状态权威、输入归属、位置、凭据与保留政策已有结论，后续契约见[首版 spec](specs/v1/spec.md)。
- 通信确认、重连、版本、大输出、取消、系统回收和省流切换按首版 spec 自主收敛；实现与设备验证仍须后续授权。
